# ⓐ 소사대(C) 합격 넷 — 「야구점수 늘 15」와 어긋난 이유

## 가설

`docs/BALANCE_BACKLOG.md`(A · 09-13)는 `hsBaseballScore`가 **늘 정확히 15**라고
적었다(프로브 7회). `SIM_REPORT_2026-09-14_final24.md`는 24판 중 lazy 넷
(#3 #6 #9 #12 · 씨앗 20260802)이 `TEAM_UNIV_SOSA`(power 2 → C 등급 ·
`minBaseballScore 25`)에 붙은 것을 보고 후보 셋을 냈다:

- (가) 수상 두 번(perAward 15 × 2 = 30)
- (나) 「늘 15」가 틀렸다
- (다) 지원·합격 판정이 `checkUniversityEligibility`를 안 탄다

## 코드 추적

1. **`calcHsBaseballScore`**(`apps/ui/src/shared/utils/universityUtils.ts:187`)는
   `psResult`(champion 100 · runnerUp 60 · semiFinal 30 · notQualified 10) +
   `awards.length × perAward(15)`을 더한다.
2. **`psResult`는 고교전에 절대 안 채워진다.** `applyProtagonistSeasonRecord`
   (`seasonCareerRecord.ts:117`)가 `postseasonResultOf(s.schedule, myTeamId)`를
   부르는데, 이 함수는 `s.schedule`에서 `phase === "postseason"`인 항목만
   본다. 그런데 그 항목을 만드는 유일한 자리 `injectLeaguePostseason`
   (`advanceWeek.ts:2511`)이 **고교·대학을 명시적으로 제외한다**:
   `SUPPORTED = ["LEAGUE_KBL", "LEAGUE_ABL", "LEAGUE_JBL", "LEAGUE_INDEPENDENT"]`.
   고교 성적은 `TOUR_HS_*` 대회로 나고 그건 `recentOutcomes`에
   `eliminated(...)`로만 남는다(psResult 아님). **A 의 원인 진단은 맞다.**
3. **실제 합격 판정은 `checkUniversityEligibility`를 안 탄다 — 하지만
   "다른 계산"을 하는 게 아니다.** 진짜 판정 자리는
   `advanceWeek.ts:1233-1252`다: `calcHsBaseballScore`(같은 함수) +
   `requirementOfPower`(같은 사다리)로 `univChoiceReqs`를 만들어
   Rust `window.projectB!.weekCalcHsAdmissions(...)`에 넘긴다.
   TS 쪽 `checkUniversityEligibility`는 **드라이버(`perfEntry.ts`)가 학교를
   고르는 후보 필터로만** 쓰인다 — 실제 합격 여부는 항상 Rust 몫이었다.
4. **Rust `calc_hs_admissions`**(`packages/engine-native/src/week_engine.rs:571-612`)가
   진짜 원인이다. 문턱을 **하드 게이트가 아니라 확률**로 쓴다:

   ```rust
   let chance = match (meets_academic, meets_baseball) {
       (true, true)   => (70.0 + a_bonus + b_bonus).min(92.0),
       (true, false)  => 28.0,   // 학점은 되는데 야구점수가 안 되도 28%
       (false, true)  => 22.0,
       (false, false) => 8.0,    // 둘 다 안 돼도 8%
   };
   ```

   **`(true, false)` 분기는 어느 학교(D 든 S 든) 를 넣어도 값이 똑같이 28.0
   이다.** `min_baseball_score`가 18 이든 70 이든 문턱을 못 채우면 보너스
   계산 자체를 안 탄다 — 사다리가 등급별로 **얼마나 어려운지는 반영되지만,
   "못 채운 상태에서 얼마나 못 채웠는지"는 확률에 안 들어간다.**

  확정됐다**(아래 결론) — 0/3 이든 1/3 이든 같은 28%(또는 8%) 분기 안의

# ⓑ 군 노말 30.9 의 분모

## 가설

`report-simruns.cjs`의 「등급 빈도 — 시즌당」은 `불완전` 표식이 없는 줄만
분모에 넣는다. 그런데 24판 군(`무대: "military"`) 줄 42개 중 20개가
`불완전` 표식 없이 노말/레어/유니크/히든 전부 0 이다 — 그래서 30.9 가
나왔다. **0 줄이 무엇인지**를 밝히는 것이 먼저다.

## 실측 — 코드 추적 + 원본 JSON

24판 원본에서 군 줄 42개를 직접 셌다(스크래치패드 스크립트 · 소스 안 고침):

- 42줄 중 20줄이 전부 0, **전부 `불완전: false`**(필러가 아니다).
- 입대(`military_enlist`)가 있는 판은 예외 없이 두 줄이 나온다: **첫 줄은
  큰 값(49/81/102/113), 둘째 줄은 정확히 0.** 입대만 있고 전역이 아직
  없는 판(#13·#16 · 시즌이 모자람)은 **한 줄만**(49) 나온다.

### 메커니즘 — 셋이 겹친다

1. **입대가 시즌을 직접 건너뛴다.** `enlistProtagonist`
   (`apps/ui/src/shared/usecases/militaryDecision.ts:38-90`)는
   `processAllLeaguesSeasonEnd`를 부른 뒤 `openMilitarySeason(seasonYear+1, …)`
   (`militaryDecision.ts:115-119`)을 호출하는데, 이건
   `seasonStore.initSeason("LEAGUE_MILITARY", …)`로 **연도를 직접 갈아
   끼운다** — 계측 워커의 바깥 루프가 그 해의 `isSeasonEnded()`를 볼
   기회가 없다(입대 시즌 자체가 통째로 건너뛰어진다).
2. **계측 워커의 필러 루프가 `prev`(등급 카운터 기준점)를 안 갱신한다.**
   `scripts/probe-a-simrun-worker.cjs:40-52`의 `못 접은 해` 처리는
   `lastSeason`·`yearAt`만 새로 잡고 **`prev`는 그대로 둔다**(주석에도
   이미 "그 해만 성적이 빈다"고 적혀 있다 — 그런데 다음 줄이 그 빈 걸
   "대신 떠안는다"는 것까지는 안 적혀 있었다). 그래서 다음 실제
   `isSeasonEnded()`가 찍힐 때 delta(`now - prev`)는 **건너뛴 시즌의
   진짜 사건(주로 프로/독립 등급 시스템에서 정상 발동한 것) 전부를
   포함한 채** 군 이름표를 달고 찍힌다. 값 49/81/102/113은 이렇게 **직전
   무대 한두 시즌의 정상치(45~52/시즌)가 그대로 넘어온 것**이다 —
   `#14`/`#20`처럼 필러가 세 개 겹치면(고교→독립→2군 전이가 한꺼번에
   밀림) 113까지 커진다.
3. **군 주간 루프는 등급 시스템을 애초에 안 탄다(설계).** `advanceWeek.ts`
   의 군 복무 분기(`careerStage === "military"`, 2636~2699행)는
   `runMilitaryLifeWeek`(별도 캘린더+뽑기 시스템)만 부르고 반환한다 —
   등급 이벤트를 발동시키는 `eventEngine`/`eventFunnel` 쪽은 아예 안
   지난다(`militaryLife.ts`에 그쪽 import 자체가 없다 — 확인함). 이건
   `docs/SIM_102_STAGE0_2026-09-12.md` 3장이 이미 밝힌 그대로다("군은
   등급 구분 자체가 이 루프에 없다"). **그래서 둘째 줄(전역 시즌)이
   정확히 0 인 것은 결함이 아니라 설계다** — `prev`가 이미 직전 줄에서
   리셋됐고, 그 뒤로 흐른 진짜 군 복무 주간은 등급 카운터에 아무것도
   더하지 않는다.

## 결론

**둘 다 「군 이벤트 빈도」가 아니라서 못 쟀다.** 0 포함(30.9/27.8)도 0 제외
(59.0/55.6)도 **군에서 실제로 무슨 일이 얼마나 났는지를 재지 않는다**:

- 0 인 줄은 "군이 조용했다"가 아니라 **"군 복무 주는 이 계수기가 원래
  못 본다"**는 뜻이다 — 설계대로다.
- 큰 값(49~113)은 "군이 활발했다"가 아니라 **"입대 직전 무대의 사건이
  새어 들어온 것"**이다 — 군과 무관하다.

`tier_rules.json seasonFreqByStage.군`(24~30)의 근거(`SIM_102_STAGE0
_2026-09-12.md` 3장 — 캘린더 22건/100주 + 비-캘린더 40.6주 × 40%)는
`militaryLife.ts`의 **독자 캘린더+뽑기 시스템**을 센 것이지 `tierCounters`
(노말/레어/유니크/히든)를 센 게 아니다. 애초에 서로 다른 계수기를 겨눈
숫자였다 — **잣대를 맞추려면 `report-simruns.cjs`가 아니라 워커가 군
복무 주마다 `runMilitaryLifeWeek`의 실제 발동(캘린더 히트 · 40% 뽑기
성공)을 따로 세야 한다.** 그 계수기는 지금 없다.

### 왜 안 고쳤나

이 물음의 규칙대로: **잣대가 report 스크립트 결함이면 고치고, 워커
결함이면 고치지 않는다.** 분자·분모 둘 다 원인은 (1) 계측 워커
(`probe-a-simrun-worker.cjs`)의 필러 처리가 `prev`를 안 되돌리는 것과
(2) 군 복무 주가 애초에 등급 시스템을 안 타는 **엔진 설계** 둘이다 —
`report-simruns.cjs`는 받은 데이터를 정직하게 집계했을 뿐이라 그 스크립트
자체엔 결함이 없다. 워커를 고치려면 **판을 다시 돌려야** 하므로(24판
280분) 여기서 손대지 않았다.

### 사용자가 정할 것 (ⓑ)

- 군 이벤트 강도를 재려면 새 계수기(군 전용 — 캘린더 히트 수 · 40% 뽑기
  발동 수)가 필요하다. 이건 **계측 도구 작업**(A/D)이지 밸런스 조정이
  아니다 — 만들지 여부와 시점을 정해 달라.
- `probe-a-simrun-worker.cjs`의 `prev` 미갱신은 군 말고 **다른 전이
  (드래프트·대학·독립)에도 같은 폭으로 영향**을 준다 — 다만 그쪽은
  둘 다 등급 시스템을 타므로 "합계가 새는 게 아니라 이름표만 어긋나는"
  정도라 지금 표의 절대값을 크게 흔들진 않는다(고교/대학/독립/프로 시즌당
  평균은 전부 40~50대로 서로 비슷해서, 어느 이름표에 잡히든 평균이 크게
  안 움직인다 — 군만 "새는 값 vs 원래 0"이라는 극단적 조합이라 두드러진다).
  이 자체를 고칠지는 별도 결정 사항이다.
