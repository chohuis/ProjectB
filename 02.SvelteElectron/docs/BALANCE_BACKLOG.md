## 12. 유망주 랭킹의 스카우트 평가 폭이 **OVR 차를 이긴다** (2026-09-07 · A 실측 · U2 곁다리)

둘 중 하나만 고쳤다.**

- **고친 것(결함)** — 평가가 `id 뒷자리 mod 3` 세 통으로만 갈렸다.
  `gcd(1000,600)=200` 때문이고, 기수마다 id 규칙이 달라 **한 학년이 통째로

- **안 고친 것(밸런스 · 여기)** — 통이 없어져도 **폭 자체가 OVR 차보다 크다.**

| 값 | 자리 | 지금 실측 | 재는 법 |
|---|---|---|---|
| 스카우트 평가 가중 **0.20** (범위 10~70) | `player_engine.rs` `calc_prospect_rank` · `hero_prospect_score` (세 자리에 같은 수가 있다) | 아래 | `npx cross-env ELECTRON_RUN_AS_NODE=1 electron scripts/probe-c-u2u6.cjs --seed 20260731 --week 20 --seasons 3` 의 「통합 상위」 줄 |

`check:tiercoverage` 의 「시즌 상한 위반 0」 줄은 규칙에서 뺐다 — 아무도
상한을 안 걸면 늘 0 이라 **아무것도 안 지키는 초록**이 된다. 상한이 선언된
판에서만 규칙으로 센다. 히든의 `careerCapPerEvent`(종당 커리어 1회)는
**그대로다** — 그건 같은 이벤트의 되풀이를 막는 것이지 시즌 상한이 아니다.

## 🔴 엔진 직접 호출로 잰 옛 표를 믿지 마라 (2026-09-08 · A · 값 변경 아님)

`random_decision_for_sim`(`runSimpleGame` 이 쓰는 결정 함수)이 **투수의 보유
구종을 안 봤다.** 네 구종을 하드코딩해 균등하게 던졌고, `grade_of` 는
arsenal 에 없는 구종에 기준값 3 을 주므로 **숙련도도 안 걸렸다.**

그래서 **엔진을 직접 부른 계측 전부**가 「구종 넷을 3등급으로 균등하게 던지는
투수」를 재고 있었다 — `audit:engine` ② · `probe:a:tempo` · `probe:a:read`.
증상은 그 표들에 이미 있었다: **구종 개수를 2~5 로 바꿔도 피안타율이 소수점
셋째 자리까지 같았다.** arsenal 이 산식에 아예 안 닿았다.

- **고쳤다** — `match_engine.rs` 의 `random_decision_for_sim` → `pick_from_arsenal`.
- **실제 플레이와 판을 돌려 잰 값은 멀쩡하다.** 화면은 사람이 자기 구종을
  고르고 NPC 는 `auto_pick_decision` 을 탄다. `BALANCE_BASELINE_101` 의
  다섯 절(E2·DR·LOC·MOR·REU)도 전부 `headless.boot()` 판이라 이 함수를 안 지난다.
- **조정 단계에서 할 일**: 위 세 계기의 **고치기 전 표는 폐기**한다. 완급
  조절(⑧)·코스 반복(⑨)·타자 노림수(⑩)·결정구(⑪)의 전후 비교를 그 표로 한
  것이 있으면 **다시 잰다** — 구종이 안 걸린 투수로 잰 값이라 방향까지는
  몰라도 폭은 못 믿는다.

## 성향 성장형의 **몸값 계수** `GROWTH_BODY_WEIGHT = 0.5` (2026-09-10 · A · 제안값 · 사용자 확정 ①)

`apps/ui/src/shared/usecases/simPersona.ts`.

**계측 전용 값이다 — 게임 밸런스가 아니다.** 성향 셋(성장·안전·대충)은 30판

고치기 전 `growthValue` 는 `bodyCost` 를 아예 안 봤다. 그래서 「피로 +15 ·

성장에서도 지던(통산 81 대 안전형 83) 원인이다.

### 어떻게 골랐나 — 판을 안 돌리고 **559개 선택지로 실측**

`scripts/probe-a-bodyweight.cjs`(`npm run probe:a:bodyweight`). 동결된
`messages/decision_templates.json` 에서 효과 있는 선택지가 둘 이상인 결정
**559개**를 다 꺼내, 계수별로 성장형이 실제로 무엇을 고르는지 센다. 판을
안 돌리므로 몇 초면 끝난다.

| 계수 | 안전형과 같은 답 | 고른 것의 몸값 평균 | 스탯 갈래를 고른 비율 |

| 0 | **41.9%** | **+2.56** | 12.7% |
| 0.25 | 63.7% | −0.13 | 12.7% |
| **0.5** | **69.9%** | **−0.97** | **12.7%** |
| 1 | 76.0% | −1.66 | 12.7% |
| 3 | 86.0% | −2.39 | 12.9% |
| 20 | 90.3% | −2.83 | 10.2% |

## `militaryDeferPenalty` 를 **FA 관심도**에서 읽는다 — 1점 = 명성 1 (2026-09-10 · A · 제안값 · 사용자 확정 ③)

`apps/ui/src/shared/utils/faEngine.ts` `generateFaOffers`.

**결함이었다** — 입대를 미룰 때마다 `militaryDeferPenalty` 가 쌓이는데
**읽는 자리가 코드 어디에도 없었다.** 대가 없는 연기라 성향과 무관하게
「미루는 게 이득」이었다.

### 왜 FA 인가

- **미필은 능력 문제가 아니라 구단의 이해 문제다.** 언제 빠질지 모르는 선수에
  구단이 큰돈을 안 건다 — 능력치를 깎으면 의미가 어긋난다.
- `fame` 은 이미 Rust `eval_fa_bid` 의 관심도로 들어간다. **소비처가 있는 값**이라
  새 경로를 안 만든다.
- **저장된 `fame` 을 안 건드린다.** 제안 계산 때만 뺀다 — 깎인 자리가 한 곳뿐이라
  추적된다. `fame` 자체를 깎으면 화면·이벤트로 흩어져 어디서 깎였는지 못 찾는다.

```ts
fame: Math.max(0, (protagonist.fame ?? 0) - (protagonist.militaryDeferPenalty ?? 0)),
```

**값: 1점 = 명성 1** (제안값). 연기 1회당 페널티가 얼마나 붙는지는 기존
`militaryDecision` 이 정한다 — 여기서는 **환산비**만 정했다. 세게/약하게는
이 한 줄의 계수로 조절한다.

## ✅ 고교 야구점수의 **팀 성적 항이 늘 0 이다** — 배선 부재 (2026-09-13 · A · **2026-09-18 고쳤다**)

D 가 프로브 일곱 번에서 `hsBaseballScore` 가 **전부 정확히 15** 인 것을 잡았다.
읽어 보니 계산 결함이 아니다:

**`calcHsBaseballScore`(`universityUtils.ts`)는 맞다. 입력이 안 채워진다.**
`psResult` 를 채우는 곳은 `seasonCareerRecord.postseasonResultOf` 하나인데

고교 성적은 **대회(`TOUR_HS_*`)** 로 나는데 그 결과가 `psResult` 로 안 들어간다.

안 붙고**, `perAward 15` 한 항만 남아 점수가 **늘 15**다.

### 왜 지금 중요한가

**사다리 위쪽이 죽은 값이 된다.** 야구점수 상한이 사실상 「수상 개수 × 15」라
C(25)·B(30)·A(45)·S(70)는 수상을 2·2·3·5회 받아야 닿는다 — 고교 3년에
그만큼 받는 판은 드물다. **24판에서 C 이상 진학이 0 이면 그건 문턱이 센 게
아니라 이 배선 때문**이다.

⚠ **이번 판에는 안 고쳤다** — 한 번에 한 변수다(24판이 문턱만 재야 한다).
고칠 자리 후보 둘: ⓐ `postseasonResultOf` 가 대회 결과(`TOUR_HS_*`)도 읽게 한다
· ⓑ `calcHsBaseballScore` 가 `psResult` 말고 대회 기록을 직접 읽는다.

## `manual_clamp` 아홉 자리 — **식은 안 건드린다** (2026-09-21 · 사용자 확정)

clippy 62 → 0 작업에서 `.max(a).min(b)` 를 `.clamp(a, b)` 로 바꾸라는 경고가
아홉 건 나왔다. **하나도 안 바꿨다.** 자리마다 `#[allow(clippy::manual_clamp)]`
와 이유 한 줄을 달아 뒀다.

| 파일 | 자리 | 무엇을 정하는 식인가 |
|---|---|---|
| `npc_sim.rs` | `clamp_stat` | NPC 능력치 하한·상한 (1~99) — 성장·감퇴가 전부 여기를 지난다 |
| `npc_sim.rs` | `calc_npc_pitching_ovr` | 투수 OVR 가중합 |
| `npc_sim.rs` | `calc_npc_batting_ovr` | 야수 OVR 가중합 |
| `player_engine.rs` | `calc_draft_success` | 드래프트 지명 확률 (5~70%) |
| `player_engine.rs` | `calc_indie_success` | 독립리그 입단 확률 (35~80%) |
| `player_engine.rs` | 성적 평점 넷 | OPS·ERA·WHIP·K9 점수 — 재계약·방출이 이 값을 본다 |

**왜 안 바꾸나 — 둘이다.**

1. **NaN 에서 동작이 갈린다.** `x.max(lo).min(hi)` 와 `x.clamp(lo, hi)` 는
   `x` 가 NaN 일 때 같은 값을 내지 않는다. 위 식들은 나눗셈(`k / ip` ·
   `ovr / potential`)이 위에 있어 NaN 이 **못 온다고 말할 수 없다.**
2. **TS 검사가 이 글자를 못박고 있다.** 같은 산식이 TS 쪽에도 있고
   (`market.ts` 의 `calcNpcPerfScore` 등) 검사가 두 쪽을 대조한다.

⚠ **밸런스 동결이 풀릴 때 같이 본다.** 그때 할 일은 「`clamp` 로 바꾸기」가
아니라 **「NaN 이 여기 올 수 있는가」를 먼저 재는 것**이다. 못 온다는 것이
확인되면 그때 아홉 자리를 한꺼번에 바꾸고 `allow` 를 지운다. 못 재면
그대로 둔다 — 지금 바꾸면 **두 변수를 같이 움직이는 것**이다.

재는 법: 아홉 자리의 입력에 NaN 을 넣는 Rust 단위 검사 하나 + 전후로
`clippy_freeze_tests`(`npc_sim.rs` · 경기 한 판 JSON 통째) 동일.

### 값 — 절대값이 아니라 **남은 머리 공간의 몫**

```
우승횟수 = max(history.titleYears.length, history.nationalTitles ?? 0)
몫 = min(0.5, 0.12 × √우승횟수 + (우승>0 이고 peakEra 있으면 0.03))
prestige = round(예산파생값 + max(0, 70 − 예산파생값) × 몫)
```

| 상수 | 값 | 왜 |
|---|---:|---|
| `PRESTIGE_CEIL` | **70** | 지금 파생 `prestige` 분포의 **최대**(SEOUL_ROYALS). 밖으로 나가면 관중·스폰서 산식이 보는 잣대가 전후로 달라진다 |
| `HISTORY_TITLE_WEIGHT` | **0.12** | √n 당. 제곱근이라 22회가 3회의 일곱 배가 아니라 **2.7배**다 |
| `HISTORY_PEAK_WEIGHT` | **0.03** | 전성기 한 줄. **우승이 있을 때만** 더한다 — 우승 0 인 팀(COASTALRAYS · SEAGULLS · SUNS)은 명문이 아니라 「제일 높이 간 해」다 |
| `HISTORY_SHARE_MAX` | **0.5** | 머리 공간의 절반까지. 우승 18회쯤에서 닿는다 |

**왜 몫인가 — 자르기가 아니라.** ① 천장을 **구조적으로** 못 넘는다(자르기로
막으면 우승 27회와 3회가 천장에서 같은 값이 된다). ② 몰락한 명문(예산이 낮아
머리 공간이 크다)이 많이 오르고 부자 명문(이미 위)은 조금 오른다 — 그게
「몰락한 명문」이라는 말의 뜻이다. **우승 0 이면 가산이 정확히 0** 이라
"같은 예산의 무명 팀"이 비교 기준으로 성립한다.

**`titleYears` 와 `nationalTitles` 는 더하지 않고 큰 쪽을 쓴다** — 28팀 중 27팀은
