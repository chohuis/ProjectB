### 1-1. 경로 전수 추적 결과 — **구조 자체는 정상** [확인]

**`age += 1`은 엔진 전체에서 `npc_sim.rs:942` 단 한 곳**(`run_offseason`은 나이를 안 건드림 — `applyAgingDecay`는 능력치 감퇴이지 나이가 아님). **이중 에이징 위험 없음** [확인].

> **결론**: 사용자가 겪은 "나이를 안 먹는다"는 **R3a-4d 이전의 과거 증상일 가능성이 높다.**

### 1-2. 졸업생의 나이가 slot.db에 반영되지 않는다 [확인]

`game.ts:2389` — `processSeasonEnd`가 스토어를 갱신할 때:

```ts
npcs: agedUpdated,                                        // 졸업생 제외
pendingDraft: [...st.pendingDraft, ...agedHsGraduated, ...agedUnivGraduated],
```

`save()`(`game.ts:598`)는 `s.npcs`만 `syncNpcs`에 넘긴다 — **`pendingDraft`는 어디서도 slot.db에 동기화되지 않는다.**
`syncNpcs`는 `INSERT OR REPLACE`(업서트, 삭제 없음)라 졸업생 행은 **직전 시즌의 나이·학년·리그(`LEAGUE_HIGHSCHOOL`)로 남는다.**

**실패 시나리오**: 3학년 NPC가 시즌 종료 → 졸업(`LEAGUE_DRAFT_POOL`, age+1) → `pendingDraft`로 이동 →
그 상태로 저장/종료 → 재시작 시 `getAllNpcs`가 slot.db를 읽으면 **졸업 전 상태(고교 3학년, 이전 나이)로 부활**한다.
드래프트가 그 세션 안에서 완료되면 `processNpcDraft`가 다시 `npcs`에 넣어 복구되지만, 그 사이 저장은 오염된다.

### 1-3. 세이브/로드 왕복이 유일한 영속화 지점이다 [확인]

주간 변이는 `gameStore.updateNpcs`(스토어만) → `save()` 시점에 `syncNpcs`로 일괄 반영된다.
`slotdb.cjs:453` 주석 스스로 "시즌 경계 벌크 동기화 (오프시즌 일괄 처리 결과 반영 전용 — 주간 변이는 개별 커맨드 사용)"라
적어뒀지만 **실제로는 주간 변이도 이 벌크 경로를 탄다**(`game.ts:597` 주석: "전환기: 주간 변이가 repo 커맨드로 전면 이관되기 전까지").
DESIGN.md §8.2 원칙 3·4(Repository 계층 / 커맨드형 변이)가 **주간 경로에서는 아직 적용 안 됨** [확인].

**함의**: `save()`가 안 불리면 그 주의 성장·부상·나이가 통째로 유실된다. "저장 안 하고 종료해서 유실" 클래스가
DESIGN.md §8.4가 선언한 것과 달리 **아직 소멸하지 않았다.**

### 2-3. 스키마 마이그레이션 러너가 없다 [확인] — Phase 4의 선결 과제

`slotdb.cjs:118-123`:
```js
db.exec(SCHEMA_SQL);                                    // CREATE TABLE IF NOT EXISTS 뿐
const cur = db.prepare("SELECT value FROM meta WHERE key='schema_version'").get();
if (!cur) { /* 최초 1회만 기록 */ }
```
`schema_version`을 **쓰기만 하고 읽어서 분기하지 않는다.** 기존 슬롯에 컬럼을 추가하면
`IF NOT EXISTS` 때문에 **조용히 반영되지 않고**, 코드는 새 컬럼이 있다고 가정한다.

**Phase 4(세이브 v4 클린 브레이크)에서 마이그레이션 인프라를 함께 깔아야 하는 근거.**
참고: OnePitch는 `PRAGMA user_version` 기반 단계별 러너로 v1~v26까지 무사히 굴렸다
(`03.OnePitch/03_설계/12_구현확정_결정요약.md` 부록).

## 5. Phase 3(기획 통합)에 넘길 사실

기획 판정에 직접 영향을 주는 조사 결과:

1. **`entities/players/`에 선수가 없다** — 172팀 이관 시 선수는 전부 런타임 Rust 생성이라는 전제는 이미 성립. 이관 대상은 팀·구장·특성·히스토리뿐.
2. **`season`이 단일 JSON 블롭이다** — 172팀 스케줄·순위·성적을 블롭 하나에 넣으면 규모가 폭증한다. Phase 4에서 `schedule`/`standings`/`season_stats` 테이블 분리가 **선택이 아니라 필수**가 될 가능성이 높다. (성능 목표 합의 시 이 점을 근거로 쓸 것)
3. **PendingAction이 17종** — OnePitch는 8종(+`pitcherChange`)으로 운영했다. 통합 기획에서 어느 쪽 목록을 정본으로 삼을지 판정 필요.
4. **`radiusGate.ts`가 이미 리그별 반경을 하드코딩** — 국내 풀 시뮬 + 해외만 반경으로 바꾸려면 이 파일이 1차 수정 대상.
