  그리고 있었다.
- 원본 `HomeDashboard.svelte`·`MessagesPage.svelte`는 **삭제했다.** 남겨두면

## 2. Phase 순서와 근거

의존성이 실제로 걸리는 곳은 **두 군데뿐**이고 나머지는 노출 빈도로 정한다.

```
제약 ①  소식(C1)이 사이드바(B2)보다 먼저다 — 내비가 가리킬 곳이 없으면 못 줄인다
제약 ②  사이드바(B2)와 "나" 통합(C2)은 같은 작업이다 — 빼는 것과 합치는 것
```

| Phase | 내용 | 완료 조건 |
|---|---|---|
| **U0** ✅ | 디자인 토큰 · 팀 색 파생 | 국내 182팀 세 대비 통과 |
| **U1** ✅ | A 진입 4화면 | 로딩→인트로→슬롯→새게임이 한 톤 |
| **U2** ✅ | B1 상단 헤더 · B3 우측 패널 | 모든 화면에 겹쳐 나오는 틀 확정 |
| **U3** ✅ | C1 **소식** 신설 | 뉴스 종류별로 실제 렌더 · 파고들기 경로 동작 |
| **U4** ✅ | B2 사이드바 6개 + C2 **나** 통합 | 기존 화면 전부 도달 가능 · 단계별 탭 |
| **U5** | **전역 지면을 밝게 뒤집는다** | 자주 보는 화면이 다 밝아진 시점 |
| **U6** | C3 리그 | 세이브왕·도루왕·대진표가 화면에 나온다 |
| **U7** | **D 경기 3화면** | 아래 §3 참조 |
| **U8** | C4 팀 · C5 사람 · C6 일정 | |
| **U9** | F 선수 상세 · 팀 상세 · 시즌종료 · 은퇴 | 성격·잠재력·득점권·상무 출신이 화면에 |
| **U10** | E 진로·계약 13 + F 나머지 | |

### 왜 이 순서인가

- **U2를 먼저** — 헤더·우측패널이 모든 화면에 겹쳐 나온다. 나중에 하면 앞서
  만든 화면들의 여백·정렬을 다시 맞춰야 한다.
- **U6(리그)이 U7(경기)보다 앞** — 리그가 **이번 라운드 구현분이 화면에 닿는
  유일한 곳**이다. 세이브왕 41개·도루왕 47개·포스트시즌 대진이 지금 만들어지는데
  볼 데가 없다.
- **U10(모달)이 마지막** — 대부분 다른 화면에서 열리므로 그 화면을 만질 때
  같이 손대는 게 자연스럽다.

### ⚠ U5의 의미

지금 전역 배경은 **어두운 채로** 있고 옮긴 화면만 `.u-page`로 밝다.
화면 52개가 어두운 인라인 스타일이라 지면을 먼저 뒤집으면 한꺼번에 깨진다.

U4까지 끝나면 자주 보는 화면(진입·소식·나·헤더·사이드바)이 거의 다 밝으므로
**그때 전역을 뒤집고**, U6~U10은 밝은 바탕 위에서 작업한다.
U5 이전까지는 "새 게임은 밝은데 메인은 어두운" 어색함이 남는다 — 알고 가는 비용이다.

## 3. 경기 화면 (U7) — 따로 기획한다

**이 게임에서 가장 큰 화면이고(2,797줄) 가장 자주 본다.** 다른 화면과 성격이
달라 같은 규칙을 그대로 적용하면 안 된다.

### 3-1. 현재 구조

`MatchPage.svelte`가 다섯 개 패널로 되어 있다:

```
base-panel          주자 상태
count-panel         볼·스트라이크·아웃
zone-panel          투구 존
pitch-select-panel  구종 선택
info-panel × 2      타자 정보 · 투수 정보
```

그 위에 라인업 패널, 아래에 교체 타이밍·경기 종료 모달.
`BaseballField.svelte`(859줄)가 구장 뷰를 그린다.

### 3-2. 두 모드를 갈라야 한다

`isProtagonistPitching`이 이미 있는데 화면은 한 벌뿐이다.

| 모드 | 상황 | 화면이 해야 할 일 |
|---|---|---|
| **등판** | 주인공이 던진다 | 구종 선택·존·피로가 주인공. 결정을 받는다 |
| **관전** | 주인공이 안 나온다 | 진행을 보여주고 넘긴다. 결정이 없다 |

관전인데 구종 선택 패널이 떠 있으면 "내가 뭘 해야 하나"로 읽힌다.
**관전 모드는 패널을 접고 진행 속도 조절만 남긴다.**

### 3-3. 유니폼 적용 원칙

| 요소 | 규칙 |
|---|---|
| 스코어보드 | `--t-dark` 바탕에 `--t-gold` 점수. **지고 있으면 상대 쪽이 금색** |
| 주자 | 45° 회전한 세 칸. 야구 관습 그대로 |
| 카운트 | 볼 `--t-accent` · 스트라이크 `--t-gold` · 아웃 `--t-dark` |
| 구종 버튼 | 테두리 `--t-dark`, 선택 시 반전 |
| 피로 | **스태미나가 낮으면 특정 구종이 흐려진다** — 선택지가 줄어드는 걸 눈으로 본다 |
| 사이드바 | **이 화면만 접는다.** 한 타석에 집중하는 순간이라 다른 데 갈 이유가 없다 |

### 3-4. 상대 팀 색

**주인공 팀 색만 쓰면 스코어보드가 한쪽만 칠해진다.** 상대 팀 색도 필요하다.

- 전역 `--t-*`는 **주인공 팀 고정**
- 상대는 `teamTokens(상대팀.colors)`를 지역 변수(`--o-*`)로 — 새 게임 확인
  카드에서 쓴 방식과 같다
- ⚠ 두 팀 색이 비슷하면 구분이 안 된다. **명도 차가 15 미만이면 상대 쪽을
  중성 회색으로 낮춘다** — 규칙을 `teamTheme.ts`에 추가해야 한다(U7에서)

### 3-5. U7을 셋으로 쪼갠다

| | 내용 | 완료 조건 |
|---|---|---|
| U7-a | 스코어보드·카운트·주자 (D1 상단) | 두 팀 색이 구분된다 |

## 5. 지켜야 할 규칙

### 5-1. 팀 색은 한 곳에서만 계산한다

`utils/teamTheme.ts` → `applyTeamTokens`가 문서 루트에 바른다.
**컴포넌트가 각자 팀 색을 읽으면 이적 한 번에 52개 화면을 고쳐야 한다.**

지역 변수(`--c-*`·`--o-*`)를 쓰는 예외는 둘뿐이다:
- 새 게임 확인 카드 — 아직 소속 확정 전
- 경기 화면의 상대 팀 — 주인공 팀과 동시에 필요

### 5-2. 파생의 함정 셋 (이미 밟았다)

- **주색을 헤더에 그대로 쓰면 안 된다.** 238팀 L\* 13~83, 130팀이 L\* > 45
- **골드를 회색과 섞으면 색조가 죽는다.** 흰색과 섞어 틴트로
- **판정은 L\* 수치가 아니라 대비다.** 헤더와 4.5:1

검사: `npm run check:teamcolors` · `vitest`(파생 10건)

### 5-3. "정본이 둘"을 만들지 않는다

이 구간에서만 세 건 나왔다 — 단계 라벨(`kbl` vs `pro_kbl`), 권역 이름,
낡은 주석("8개"인데 실제 102개).

**화면에 표를 새로 만들기 전에 `utils/`에 같은 게 있는지 본다.**
`Record<유니온, string>`으로 선언하면 값이 늘 때 컴파일이 깨진다.

### 5-4. 매 Phase 끝에 회귀를 돌린다

```
npm test                  vitest
npm run check:teamcolors  팀 색 전수
npx tsc --noEmit          (apps/ui에서)
npx svelte-check --threshold error
```

기준선: `vitest 82` · `tsc 7` · `svelte-check 60` · `cargo 171`

### 5-5. 표본으로 통과한 검사는 검사가 아니다
