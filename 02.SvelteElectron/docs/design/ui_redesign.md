## 2. Phase 순서와 근거

```
제약 ①  소식(C1)이 사이드바(B2)보다 먼저다 — 내비가 가리킬 곳이 없으면 못 줄인다
제약 ②  사이드바(B2)와 "나" 통합(C2)은 같은 작업이다 — 빼는 것과 합치는 것
```

> ⚠ **U9를 U7보다 먼저 했다 (2026-08-05).** 구장 27장이 도착해 경기 화면의
> 전제(구장별 그림·티어별 좌표)가 그때 확정됐고, 그 사이 U9가 구장과
> 독립이라 먼저 끝냈다. 남은 순서는 **§3-9**가 정본이다.

> ⚠ **U5를 U6·U8 뒤로 옮겼다 (2026-08-05).** 번호는 그대로 두고 순서만 바꾼다 —
> 앞선 커밋 메시지들이 번호로 남아 있어 다시 매기면 이력이 어긋난다.

### 왜 이 순서인가

- **U2를 먼저** — 헤더·우측패널이 모든 화면에 겹쳐 나온다. 나중에 하면 앞서
  만든 화면들의 여백·정렬을 다시 맞춰야 한다.
- **U6(리그)이 가장 먼저** — 리그가 **이번 라운드 구현분이 화면에 닿는
  유일한 곳**이다. 세이브왕 41개·도루왕 47개·포스트시즌 대진이 지금 만들어지는데
  볼 데가 없다. 미루면 그만큼 "만들었는데 아무도 안 받는" 상태가 길어진다.
- **U10(모달)이 마지막** — 대부분 다른 화면에서 열리므로 그 화면을 만질 때
  같이 손대는 게 자연스럽다.

### ⚠ U5를 왜 뒤로 미뤘나 (2026-08-05 재검토)

원래 계획은 "U4까지 끝나면 자주 보는 화면이 거의 다 밝으니 그때 뒤집는다"였다.
**U4를 끝내고 실측해 보니 전제가 안 맞았다.**

내비 여섯 중 옮긴 건 **둘뿐이다** — 소식·나. 팀·리그·사람·일정 넷이 남았고,
그 넷의 최상위 `.page`는 **배경도 글자색도 안 정한다:**

```css
/* LeaguePage · SchedulePage · TeamPage · PeoplePage 공통 */
.page { display: grid; ... }   /* background 없음 · color 없음 */
h2, h3, p { margin: 0; }       /* 색 없음 */
```

안쪽 카드는 자기 배경과 글자색을 들고 있어 멀쩡하지만, **카드 밖 제목들이
전역 `color: #f4f7ff`를 물려받는다.** 지금 뒤집으면 흰 바탕에 흰 글씨가 된다 —
보기 싫은 정도가 아니라 안 보인다.

그리고 지금 뒤집어도 **얻는 게 없다.** 남은 화면들이 자기 배경을 들고 있어서
뒤집기가 "이제 고쳐야 한다"는 강제력으로 작동하지 않는다.

U6·U8을 먼저 하면 여섯 목적지가 전부 밝아지고, 그때 U5는
**`.u-page`를 여섯 군데에서 떼면서 전역으로 올리는 정리 작업**이 된다.
깨뜨리는 이벤트가 아니라 줄이는 작업이다.

그때까지는 "소식·나는 밝은데 리그·팀은 어두운" 어색함이 남는다 — 알고 가는 비용이다.

버튼은 경기 종료 모달에만 있다. 경기 도중 나가려면 Esc를 알아야 한다.

`MatchPage`를 통째로 렌더한다 — 헤더·사이드바·우측패널이 전부 없다.
**기존 계획서의 "이 화면만 사이드바를 접는다"는 이미 참이었다.**
문제는 반대다: 날짜·주차·상대 팀 같은 맥락이 하나도 안 남는다.

**④ 라인업이 문자열 배열이다.** `awayLineup: string[]`을 `<li>{item}</li>`로
그린다 — 지금 타석·다음 타자·교체 여부를 표시할 구조가 없다.

### 3-5. 유니폼 적용

| 요소 | 규칙 |
|---|---|
| 스코어보드 | **중성 바탕** · 내 팀 행만 `--t-accent` 띠 · 팀 식별은 마크(§3-6) |
| 카운트 | 스트라이크 `--t-gold` · 볼 `--ink-on-dark` · 아웃 `--bad` |

| 피로 | **스태미나가 낮으면 특정 구종이 흐려진다** — 선택지가 줄어드는 걸 눈으로 본다 |

계열을 명시해 §5-5b 검사를 통과시킨다.

### 3-6. 상대 팀 구분 — **색으로 하지 않는다** (2026-08-05 폐기·재작성)

원안은 이랬다: 상대 팀을 `--o-*` 지역 변수로 주고, 두 팀이 비슷하면
명도 차 15 기준으로 상대를 중성으로 낮춘다.

**만들어서 전수로 재 보니 성립하지 않는 설계였다.**

```
모든 팀 헤더 L*      25.2 ~ 26.4    ← HEADER_MAX_L=26이 238팀을 전부 눌렀다
ΔL* < 15인 짝        100%
명도·색상·채도가 다 가까운 짝   30.8%  (같은 리그 7,383짝 중 2,273)
어떤 중성색을 써도    113~129팀과 겹친다
```

**명도 축이 죽어 있다.** 헤더는 흰 글씨를 얹으려고 전부 L\*26으로 눌리므로
명도로 가를 수 없고, 중성색도 같은 L\*26이라 도망갈 자리가 없다. 원색끼리
비교해도 구분 안 되는 짝이 9.2% 남는다 — **100%가 안 되면 규칙이 아니다.**

그리고 이건 §0의 확정 사항과도 어긋났다:

> 팀 색 범위 — **헤더·강조만.** 본문·표는 중성. 어느 팀이든 가독성이 같아야 한다.

**스코어보드는 표다.** 표를 팀 색으로 칠하려던 것 자체가 원칙 위반이었다.

**대신 이미 있는 것을 쓴다 — 팀 마크.**
마크는 같은 그룹 안에서 (외곽·문양) 짝이 안 겹치는 게 테스트로 보증된다(§5-6).
색이 못 하는 일을 형태가 한다.

| 요소 | 규칙 |
|---|---|
| 스코어보드 두 행 | **중성 바탕.** 팀 식별은 마크 + 이름 |
| 내 팀 행 | `--t-accent` 좌측 띠 + 굵게 — **내 팀만 표시**하면 되고, 그건 항상 성립한다 |
| 상대 팀 행 | 표시 없음 |

`--o-*`는 만들지 않는다. §5-1의 "지역 변수를 쓰는 예외 둘" 중 경기 화면
항목은 **취소**다 — 예외가 하나(새 게임 확인 카드)로 준다.

> 이 절은 코드를 먼저 쓰고 전수 검사에서 되돌린 결과다. 검사가 없었으면
> 30.8%의 대진에서 두 팀이 같은 색으로 보이는 채로 나갔을 것이다.

### 3-7. 확정 배치 — "콘솔 + 박스스코어" (후보 C+D 혼합)

후보 6안을 그려 본 뒤 **C(콘솔)와 D(박스스코어)를 섞은 것**으로 정했다.
지금 화면의 문제는 패널이 부족한 게 아니라 **오른쪽 여섯 칸이 서로 자리를
빼앗는 것**이었다. 열을 셋으로 갈라 그 싸움을 없앤다.

```
└────────────────────┴────────────────────────┴────────────────────────────┘
```

**⚠ 구장 뷰는 관전 모드에서도 키우지 않는다.**
후보 중에는 관전일 때 구장을 크게 쓰는 안이 있었는데 버렸다. 구장 그림은
**구장당 한 장**만 두는 게 원칙이고(27장), 확대하면 그 한 장으로는 도트가
뭉개져 **구장마다 큰 판을 하나씩 더 그려야 한다.** 27장이 54장이 된다.
관전에서 남는 자리는 중계와 라인업이 가져간다 — 구장이 아니라.

> 이 절은 대화에서만 정해졌다가 compact로 유실돼 2026-08-05에 복원했다.
> 위 조감도가 그때 고른 그림과 다르면 이 문서를 고칠 것 — **정본은 여기다.**

## 5. 지켜야 할 규칙

### 5-1. 팀 색은 한 곳에서만 계산한다

`utils/teamTheme.ts` → `applyTeamTokens`가 문서 루트에 바른다.
**컴포넌트가 각자 팀 색을 읽으면 이적 한 번에 52개 화면을 고쳐야 한다.**

지역 변수(`--c-*`)를 쓰는 예외는 **하나뿐이다**:
- 새 게임 확인 카드 — 아직 소속 확정 전

> 예전엔 "경기 화면의 상대 팀"도 예외였다. **U7에서 취소했다** — 두 팀을
> 색으로 가르는 게 애초에 불가능하다는 걸 전수 측정으로 확인했다(§3-6).

### 5-2. 파생의 함정 셋 (이미 밟았다)

- **주색을 헤더에 그대로 쓰면 안 된다.** 238팀 L\* 13~83, 130팀이 L\* > 45
- **골드를 회색과 섞으면 색조가 죽는다.** 흰색과 섞어 틴트로
- **판정은 L\* 수치가 아니라 대비다.** 헤더와 4.5:1

검사: `npm run check:teamcolors` · `vitest`(파생 10건)

### 5-3. "정본이 둘"을 만들지 않는다

이 구간에서만 세 건 나왔다 — 단계 라벨(`kbl` vs `pro_kbl`), 권역 이름,
낡은 주석("8개"인데 실제 102개).

**화면에 표를 새로 만들기 전에 `utils/`에 같은 게 있는지 본다.**
`Record<유니온, string>`으로 선언하면 값이 늘 때 컴파일이 깨진다.

### 5-4. 매 Phase 끝에 회귀를 돌린다

```
npm test                  vitest
npm run check:teamcolors  팀 색 전수
npx tsc --noEmit          (apps/ui에서)
npx svelte-check --threshold error
```

기준선: `vitest 118` · `tsc 7` · `svelte-check 60` · `cargo 171`

### 5-6. 팀 마크는 그림이 아니라 데이터다

238팀에 로고를 그리는 건 현실적이지 않다(고교만 102팀이고 전부 가상의 학교다).
`utils/teamMark.ts`가 팀 색 두 개와 이름으로 SVG를 조립한다 —
**외곽 5 × 문양 12 × 패턴 4**, 파일 0개.

같은 그룹(고교=권역, 나머지=리그) 안에서 **(외곽·문양) 짝이 안 겹친다.**
가장 큰 그룹이 대학 50팀이고 `lcm(5,12)=60`이라 성립한다 — 테스트가 이 전제도 잰다.

⚠ 이 자리에서 두 번 틀렸다.
- 키워드 문양을 번호 배정 위에 **덮어썼다** → 다른 팀과 충돌(4건).
  덮어쓰지 말고 **자리를 맞바꿔야** 일대일 대응이 유지된다
- 12팀 이하 그룹은 `p % 12`로 뒤쪽 문양에 **닿을 수 없다** → KBL 로열스가
  왕관을 못 받았다. 작은 그룹은 자리에 안 묶고 뜻을 그대로 존중한다

### 5-5b. 어두운 섬 검사 (U5 신설)

전역이 밝아졌으므로 **아직 안 옮긴 어두운 화면은 자기 글자색을 스스로
정해야 한다.** 안 정하면 전역 `--ink`(거의 검정)를 물려받아 검은 바탕에
검은 글씨가 된다. `darkIsland.test.ts`가 매번 전수로 본다.

⚠ 이 검사를 처음 "글자 명도 > 0.3"으로 짰다가 `#2a1010` 위의 `#e07070`
(명도 0.285 · 대비 4.4:1)을 결함으로 잘못 잡았다. **§5-2와 같은 실수다 —
판정은 명도가 아니라 대비다.** 세 번째로 같은 자리를 밟았다.

검사 대상은 **아직 안 옮긴 파일뿐이다.** 토큰을 쓰는 파일에 남은 어두운
hex는 배지·등급처럼 의도적으로 고정한 색이고, 그 글자색은 부모 규칙에 있어
규칙 단위 검사가 못 따라간다.

### 5-5. 표본으로 통과한 검사는 검사가 아니다

U2에서 헤더의 **주 버튼과 등번호**를 금색-헤더 짝에 얹었다. 그 짝을 보증하던
`teamTheme.test.ts`는 **손으로 고른 5색**만 보고 있었다 — 182팀 중 하나라도
무너지면 그 팀을 고른 플레이어는 게임 내내 안 읽히는 버튼을 본다.

`refs.json`을 직접 읽어 **국내 182팀 전수**로 바꿨다(3건 추가). 데이터를 못 읽으면
0팀으로 조용히 통과하므로 **"150팀 넘게 읽혔다"는 가드 테스트를 같이 둔다.**
