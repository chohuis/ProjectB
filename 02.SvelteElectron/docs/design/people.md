## 0. 왜 다시 설계하는가

v2에서 세계가 104팀 → **206팀**(국내182 + 해외24)으로 커지면서 기존 방식이 무너졌다.

| | v1 현행 | v2 필요량 | 배수 |
|---|---:|---:|---:|
| 팀 | 104 | 206 | 2.0배 |
| 스태프 | 373 | **~1,240** | 3.3배 |
| 선수 | ~474 | **~4,400** | 9.3배 |

그리고 **현행 스태프 373개 JSON은 손 저작물이 아니다** — 실측 결과:

| 필드 | 고유값 / 전체 |
|---|---|
| `coach.specialty` | 7 / 242 |
| `coach.trainingBuffs` | 6 / 242 |
| `manager.style` | 9 / 103 |
| `owner.ownershipStyle` | 6 / 28 |

전부 템플릿 조합으로 **스크립트가 생성한 결과물**이다(`scripts/generate_team_jsons.cjs` 등).
즉 DESIGN.md §8.3이 *"생성 결과물을 저장해두고 스크립트로 사후 수정하는 패턴 금지"* 로 폐기한 것의
**마지막 잔재**다. 선수 16,075개를 지운 것과 같은 이유로 지워야 할 대상인데 스태프만 살아남았다.

## 1. 원칙

### 1-1. 모든 인물은 런타임 절차 생성

**손 저작 JSON을 두지 않는다.** git에 남는 것은 **생성 규칙**뿐이다.

```
master.db (정의)                    slot.db (상태)
├─ 생성 규칙 (스탯 밴드·비율)   ──▶  ├─ npc    (선수)
├─ 이름 풀 (ko/en/jp)                └─ staff  (감독·코치·구단주)
├─ 성격 가중치
└─ 팀·구장·특성·히스토리 (고정)
```

- `worldSeed` 결정적 — 같은 시드 = 같은 세계.
- **규칙을 고치면 새 게임에 즉시 반영**된다. 결과물을 스크립트로 땜질하는 경로가 아예 없다.
- 폐기: `resource/data/master/entities/players/*.json` **374파일** + `_index.json` 수동 동기화
  (과거 51회 커밋된 핫스팟).

### 1-2. 선수와 스태프는 **다른 테이블**

```sql
CREATE TABLE npc   (npc_id   TEXT PRIMARY KEY, ...);  -- 선수만
CREATE TABLE staff (staff_id TEXT PRIMARY KEY, ...);  -- 감독·코치·구단주
```

**근거**: OnePitch는 스태프를 `npc` 테이블에 동거시키고 `position` 컬럼으로 구분했다.
그 결과 `position NOT IN ('감독','코치','구단주')` 필터가 **7곳에 필요**했고
**5회 이상 누락 버그**가 났다 —

- 감독·코치·구단주가 실제 **타순에 섞여 타석에 섬**(스탯 키가 안 맞아 전원 50/50/50으로)
- 경기마다 **피로도가 쌓임**
- 주간 **성장 처리를 받음**
- **트레이드 후보**에 오름
- 로스터 목록·세대교체 인원 카운트에 포함

테이블을 나누면 `SELECT * FROM npc`가 **구조적으로** 스태프를 못 집는다. 필터를 잊을 수가 없다.

**공통 조회가 필요한 곳**(관계도·이름 표시·거래 기록)은 SQL VIEW로 해결한다:

```sql
CREATE VIEW person AS
  SELECT npc_id AS person_id, name, 'player' AS kind, current_team AS team_id FROM npc
  UNION ALL
  SELECT staff_id, name, role, team_id FROM staff;
```

### 1-3. 정의 데이터는 CSV/TOML 시드 → master.db

| 성격 | 포맷 | 예 |
|---|---|---|
| **표** (행이 많고 열이 고정) | **CSV** | `teams.csv` · `schools.csv` · `stadiums.csv` · `team_traits.csv` · `name_pools.csv` |
| **규칙** (중첩·가변) | **TOML** | `generation_rules.toml` · `personality_rules.toml` · `staff_rules.toml`(신규) |

- 빌드 시 master.db 테이블로 주입(`npm run build:masterdb`).
- git diff가 사람이 읽을 수 있고, `_index.json` 동기화 문제가 소멸한다.
- **`resource/data/seeds/onepitch/` 16파일이 이미 이 포맷**이다 — 이관 대상이자 참조 구현.

## 2. 생성

### 2-1. 시점 = 새 게임 시 국내 전원 일괄

```
새 게임
 └─ generateWorld(worldSeed)
     ├─ 국내 182팀 선수  ~4,400명  → npc
     ├─ 국내 182팀 스태프 ~1,090명 → staff
     │    감독 182 + 구단주 182 + 코치 (팀 자원 등급별 0~8, 평균 ~4) ~728
     └─ 해외 ABL·JBL 24팀 = Lazy (진출 확정 시)
```

- **Lazy를 국내에서 없애는 이유**: 172팀이 상시 존재하는 세계에서 "이 팀 선수가 아직 없을 수 있다"를
  모든 조회 경로가 고려해야 하면 버그가 난다. 실제로 v1의 드래프트 풀 부족 버그가 정확히 이 원인이었다
  (`64 < 80` → 대학·독립 리그 미활성화).
- ⚠ **트랜잭션 필수**: OnePitch는 일정 INSERT 루프를 트랜잭션으로 안 감싸 **41.4초 → 1.46초(28배)** 를 겪었다.
  5,500명 INSERT는 반드시 리그 단위 트랜잭션으로 묶는다.

### 2-2. 코치 인원 = 팀 자원 등급 연동

| 자원 | 코치 수 |
|---|---|
| 부유 | 6~8 |
| 안정 | 4~6 |
| 알뜰 | 2~4 |
| 궁핍 | 0~2 |

- **팀 선택의 실질적 격차**를 만드는 장치. 궁핍한 팀은 코치가 아예 없을 수 있고,
  그 공백을 [개인 재정](../../DESIGN.md#73-v2-신규-흡수-시스템)의 개인 트레이닝 구독으로 사비를 들여 메운다.
- 코치 역할은 6종(투수·타격·주루·컨디셔닝·멘탈·전력분석) 순환 배정.

### 2-3. ID 규약

```
선수    npc:<worldSeed>_<league>_<seq>          기존 roster_gen 규약 유지
신입생  npc:<worldSeed>_<league>_fr<season>_<seq>
스태프  staff:<teamId>_<role><seq>              팀에 종속 — 이동 시에도 ID 불변
```

- 스태프 ID를 팀 기준으로 잡되 **이동해도 ID는 안 바꾼다**(관계도가 깨지지 않게).
- 레거시 `COA_`/`MNG_`/`OWN_` 접두사는 폐기.

## 3. 생멸 (신규 — 세계를 살아있게)

정적 JSON 시절엔 없던 개념. 20시즌짜리 커리어에서 감독이 그대로면 세계가 죽어 보인다.

### 3-1. 나이 · 은퇴

- 스태프도 매 시즌 나이 +1. 고령이면 은퇴 확률 상승.
- 은퇴 시 빈 자리는 **신규 생성** 또는 **타팀 스태프 이동**으로 충원.

### 3-2. 경질 · 이동

- **감독 경질**: 팀 성적 부진이 누적되면 경질. 구단주의 `patience`가 임계값을 좌우한다
  (스태프 15종 배선의 실사용처 중 하나).
- **이동**: 좋은 성적을 낸 스태프가 더 좋은 팀으로 옮길 수 있다.
- 서사 효과: *"우리 감독이 잘렸다"* 가 사건이 되고, **관계도가 리셋되는 긴장**이 생긴다.
  주인공이 감독과 쌓은 신뢰가 역할 배정에 직결되므로 실질적 손실이기도 하다.

### 3-3. 경력 성장

- 시즌을 거칠수록 지도력·전술 등이 **완만히 상승**, 고령에서 둔화.
- **신진 감독 vs 베테랑 감독**의 차이가 생기고, 약팀이 신진을 키우는 서사가 가능해진다.
- 선수의 성장곡선과 달리 **완만하게** — 스태프가 몇 시즌 만에 최상급이 되면 팀 격차가 무너진다.

## 4. 관계도

**대상 = 스태프 전원 + 팀동료.** 주인공 기준 **1:N**만 추적한다(NPC끼리의 관계는 만들지 않는다).

| 대상 | 무엇에 영향 |
|---|---|
| 감독 | **역할 배정 · 콜업 우선순위** (신뢰도가 곧 기회) |
| 코치 | 담당 영역 **훈련 효율** |
| 구단주 | 재계약·방출 판정의 인내심 보정 |
| 팀동료 | 이벤트 분기 · 사기 · "동료 상태" 뉴스의 실측 근거 |

- 스케일: 소속팀 최대 ~55명(선수 45 + 스태프 10) × 이적 이력 누적 = **수백 행** 수준. 감당 가능.
- 값 체계는 OnePitch 안을 채택 — **−100~100, 7단계 라벨**(숫자 비노출).
- **팀 이동 시 관계 처리**(유지 / 감쇠 / 리셋)는 구현 단계에서 확정 — 이 문서의 열린 항목.

> 이 결정으로 [뉴스·미디어](../../DESIGN.md#73-v2-신규-흡수-시스템)의 "동료 개인기록 소식"과
> 콘텐츠의 "동료 상태 기반 이벤트"가 **확률형 근사에서 실측 기반으로** 바뀐다.
> OnePitch가 팀동료 관계 데이터가 없어 전부 감독 관계도로 근사했던 부분이다.

| 항목 | 확정 |

| 리그 보정 | 고교 0 · 독립 +2 · 대학 +4 · 프로 +10 (중앙값에 가산) |
| 전력★ 보정 | `(power − 3) × 3` |
| 자원 → 코치 수 | 부유 6~8 · 안정 4~6 · 알뜰 2~4 · 궁핍 0~2 |
| 자원 → 구단주 성향 | 부유 예산 +18 · 궁핍 −18 (facilityInvestment도 연동) |

| **능력치 스키마** | 감독은 **Rust `ManagerStats` 5종**(tacticalIQ·bullpenRead·offenseMind·motivator·clutchDecision) |

> ⚠ **구 JSON은 감독 스탯을 `tactics`/`decision`/`rotationMgmt`/... 로 저장했는데

> **감독 능력치가 매치 엔진에 하나도 전달되지 않았다**(전부 기본값 50).
> 6A에서 Rust 쪽 이름으로 통일했다 — 판정 이력은 [_ledger.md](_ledger.md) P6-2.
