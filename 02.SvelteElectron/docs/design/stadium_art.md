## 0. 먼저 직답 — 내가 그릴 수는 없다

**나(Claude)는 이 환경에서 이미지를 생성하지 못한다.** 코드는 쓸 수 있지만
픽셀아트를 그리는 기능이 없다. SVG·캔버스로 절차 생성하는 건 가능한데,

대신 내가 만들 수 있는 것은 분명하다 — §5에 정리했다.
요약하면 **그림을 뺀 나머지 전부**다: 규격·좌표 검사기·27장 파라미터·
빌드 파이프라인·화면 배선.

## 2. ⚠ 결정적 제약 — 좌표가 그림에 박혀 있다

`MatchPage.svelte`의 좌표는 **1000×920 공간의 절대값**이고
`probaseball.gif` 한 장에 맞춰 손으로 맞춘 것이다.

```
DEFENSE_RETRO_BASE   P 497,548 · C 497,800 · 1B 710,588 · 2B 600,508
                     SS 387,508 · 3B 272,588 · LF 242,518 · CF 497,434 · RF 752,518
retroField           홈 497,790 · 1루 715,580 · 2루 497,454 · 3루 280,580 · 마운드 497,548
타자                 홈 ±34, y−22        주자  1루 +14,−18 / 2루 0,−20 / 3루 −14,−18
```

**27장이 서로 다른 기하로 그려지면 좌표도 27벌이 된다.** 구장마다 아홉 명 +
베이스 다섯 + 타자·주자 오프셋을 손으로 다시 맞춰야 하고, 한 장이라도 어긋나면
수비수가 관중석에 서거나 주자가 잔디에 뜬다.

> **그래서 이 작업의 진짜 요구사항은 "27장을 그린다"가 아니라
> "다이아몬드가 픽셀 단위로 동일한 27장을 그린다"이다.**

이걸 사람 눈으로 지키는 건 불가능에 가깝다. 아래 §3이 그 해법이다.

## 3. 계획 — 레이어로 쪼갠다

한 장을 통으로 그리지 않고 **네 겹**으로 나눈다. 아래 두 겹은 27장이 전부 같고,
위 두 겹만 구장마다 다르다.

```
 ┌─ L4  전경 (더그아웃 · 철망 · 파울폴)      구장별 · 소품 수준
 │  L3  관중석 + 펜스 + 광고보드            구장별 · 팀 색이 여기 들어간다
 │  L2  배경 (하늘 · 산 · 도시 · 건물)       구장별 · 가장 크게 다르다
 └─ L1  경기장면 (잔디 · 흙 · 라인 · 베이스)  ★ 27장 전부 동일 — 좌표의 근거
```

**L1을 고정하면 좌표 문제가 구조적으로 사라진다.** 기존 `probaseball.gif`에서
한 번만 떼어내 27장에 그대로 재사용한다. 손으로 지키는 규율이 아니라
**만드는 방식이 보장**한다.

### 3-1. 구장 특성은 어디에 반영되나

| 특성 | 반영 층 | 방법 |
|---|---|---|
| 파크팩터 (타자친화/투수친화/중립) | **L3** | 펜스 높이 + 거리 표기 (타자 100~105m · 중립 110 · 투수 118~125) |
| 티어 (고교·대학·독립·프로) | **L2·L3** | 관중 규모 · 조명탑 유무 · 시설 등급 |
| 연고 도시 | **L2** | 서울=고층 스카이라인 · 부산=바다·산 · 제주=오름 · 춘천=호수 |
| 팀 색 (프로 10팀) | **L3** | 좌석·광고보드 주조색 — `refs.json`의 `colors[0]` |

⚠ **파크팩터를 L1으로 표현하면 안 된다.** 펜스를 실제로 당기면 외야 잔디 모양이
바뀌고 L1 고정이 깨진다. **거리 표기 숫자와 펜스 높이(L3)로만** 나타낸다 —
어차피 엔진의 파크팩터는 그림과 무관하게 수치로 돈다.

### 3-2. 그러면 그림 작업량이 얼마인가

| 층 | 필요 장수 | 난이도 |
|---|---|---|
| L1 경기장면 | **1장** (기존 것 추출) | 없음 — 이미 있다 |
| L2 배경 | **9종** (도시 6 + 산 + 바다 + 캠퍼스) | 중 — 화면 위 40%만 |
| L3 관중석·펜스 | **4종** (프로·대학·독립·고교) × 색 변주 | 중 |
| L4 전경 | **3종** (콘크리트·목재·철망) | 하 |

**27장을 27번 그리는 게 아니라 16종의 조각을 조합한다.**
고교 8구장은 L2 배경만 다르고(제주=오름 / 춘천=호수 / 서울=주택가), 나머지는 공유한다.

⚠ 단, **고교는 L1이 다르다** — 외야까지 흙바닥이다. 고교용 L1을 하나 더 만들어
L1이 2종(잔디형·흙형)이 된다.

## 5. 용량 예산 (실측)

| 포맷 | 1장 | 27장 |
|---|---|---|
| 원본 GIF 16프레임 | 10.9 MB | **294 MB** ← 불가 |
| PNG-256 1306px | 603 KB | 15.9 MB |
| WebP q92 1306px | 588 KB | 15.5 MB |
| **WebP q92 1000px** | **371 KB** | **9.8 MB** ← 권장 |
| WebP q80 1000px | 210 KB | 5.5 MB |

**1000px WebP q92를 권장한다.** 좌표계가 1000×920이라 배율이 1:1이고,
화면 실제 표시 폭이 400~600px이므로 원본 1306px은 과하다.
지금 3장(15.4 MB)보다 **27장이 오히려 작다.**

⚠ WebP는 손실 압축이라 **픽셀아트 경계가 뭉갤 수 있다.** q92에서 육안 확인이
필요하고, 안 되면 PNG-256(15.9 MB)으로 간다. 파일 크기보다 도트가 우선이다.

## 6. 누가 무엇을 하나

### 내가 할 수 있는 것 (그림 빼고 전부)

| | 산출물 |
|---|---|
| 규격서 | 캔버스 1000×920 · L1 고정 영역 좌표 · 층별 알파 규칙 · 팔레트 상한 |
| **좌표 검사기** | 후보 이미지의 다이아몬드가 기준과 몇 픽셀 어긋났는지 자동 판정. 27장 전수 |
| L1 추출 | 기존 GIF에서 경기장면 층을 떼어내는 스크립트 |
| 합성 파이프라인 | L1~L4 → 27장 · 팔레트 양자화 · WebP 변환 · 매니페스트 |
| 27장 파라미터 | 위 §4 표를 JSON으로 (`stadium_art.json`) |
| 화면 배선 | `href="/park/probaseball.gif"` 하드코딩 → 구장별 선택 |
| 회귀 | 27장 전수 검사 + 용량 상한 테스트 |

### 사람(또는 외부 이미지 도구)이 해야 하는 것

**L2 배경 9종 · L3 관중석 4종 · L4 전경 3종 · 고교용 L1 1종 = 17장의 조각.**

외부 이미지 모델을 쓴다면 **L2(배경)에만 쓰는 게 안전하다.** 화면 위 40%이고
기하 제약이 없어 실패해도 좌표가 안 깨진다. L1·L3은 기하가 걸려 있어
이미지 모델로는 일관성을 못 맞춘다.

## 7. 순서

```
S1  L1 추출 + 좌표 검사기          ← 나. 여기부터 시작해야 나머지가 검증된다
S2  규격서 + 27장 파라미터 JSON     ← 나
S3  조각 17장 제작                 ← 사람/외부 도구
S4  합성 파이프라인 → 27장 생성     ← 나
S5  화면 배선 + 전수 검사           ← 나
```

**S1을 먼저 하는 이유**: 검사기가 없으면 S3에서 만든 그림이 맞는지 알 방법이 없다.
지금까지 이 프로젝트에서 반복된 결함이 "검사 전제가 현실과 다름"이었고,
그림 27장은 **눈으로만 보면 반드시 놓친다.**

⚠ **S3이 이 계획의 유일한 병목이다.** 나머지는 전부 자동화된다.
S3을 못 하면 대안은 하나뿐이다 — 기존 3장을 티어별로 쓰고(현행 계획 A),
구장 이름만 다르게 표시한다.
