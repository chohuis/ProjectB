## 1. 무엇이 문제였나 (한 줄씩)

1. **루프가 안 닫혀 있다.** 구종을 배워도 자동 시뮬은 안 본다 —
   `SimPitcher`에 구종 배열 자체가 없고, 구종 선택이 하드코딩이다.
   숙련도는 **배우는 속도만 늦추는 계수**로 쓰이고 결과에는 안 닿는다.
2. **정본이 넷이다.** 프로그램 표가 마스터 JSON · Rust · 훈련 화면 · 일정 화면에
   각각 있고 피로 수치가 서로 다르다.
3. **화면이 거짓말을 한다.** 기본 계획에서 화면은 피로 +7, 엔진은 −4.25.
   부호가 반대다.
4. **배선이 끊겨 조용히 죽은 것들** — 화면이 저장하는 프로그램 id 12개 중 10개가
   마스터 JSON에 없어 `focus` 조회가 실패하고, 그 결과 코치 관계와 훈련 효율
   보너스가 안 붙는다.

**"밸런스가 안 좋다"가 아니라 "연결이 안 돼 있다"가 진단이다.**
그래서 수치 조정이 아니라 연결부터 만든다.

## 2. 목표

### 2-1. 주인공 성장 곡선 (측정 대상)

NPC는 `growth.md`에 나이별 목표 곡선이 있고 `test:growth` G3가 대조한다.
**주인공에겐 그게 없다.** 같은 규율을 세운다.

| 구간 | 목표 OVR 궤적 | 근거 |
|---|---|---|
| 고교 3년 | 55 → 68 안팎 | NPC 고졸과 같은 눈높이여야 드래프트 순위가 말이 된다 |
| 대학 4년 | 62 → 74 안팎 | `growth.md`의 NPC 대졸과 대조 |
| 프로 초반 | 완만 | 잠재상한 감쇠가 벽 역할 |

⚠ **위 숫자는 NPC 목표를 옮겨 적은 것이다.** 주인공은 플레이어가 슬롯을
고르므로 "잘 고른 경우"와 "대충 고른 경우"의 폭이 있어야 한다.
**폭을 얼마로 둘지가 Phase 0 실측 뒤 결정할 첫 번째 수치다.**

### 2-2. 플레이어가 매주 내리는 결정

지금은 슬롯 세 칸을 한 번 채우면 시즌 내내 바꿀 이유가 없다.
재설계 뒤에는 아래가 **실제 선택**이 되어야 한다.

- 무엇을 올릴까 (스탯 배분)
- 피로를 어디까지 밀까 (구간 승수 1.5/2.5/4.0이 벌이라 밀면 대가가 크다)
- **구종을 지금 배울까, 오프시즌까지 기다릴까** ← 폼 무너짐이 만드는 새 축

## 3. 설계

### 3-1. 정본은 하나 — 데이터 파일

**규칙은 데이터로**가 프로젝트 원칙이므로 **마스터 데이터를 정본**으로 삼고
Rust가 그걸 받는다. (지금은 Rust 하드코딩이 실제로 도는 값이므로,
**Rust 표의 수치를 데이터로 옮겨 적는 것**이 시작점이다 — 반대로 하면
밸런스가 통째로 바뀐다.)

```
resource/data/master/training/programs.json     ← 정본 (투수·타자 통합)
   ↓ masterStore.trainingPrograms
   ├→ TrainingPage      카드 표시 (하드코딩 12종 제거)
   ├→ SchedulePage      이름 표시 (PROGRAM_TITLE 제거)
   └→ calcTrainingGrowth 파라미터로 Rust에 전달 (get_program 하드코딩 제거)
```

- **id를 하나로 통일한다.** 지금 구버전(`TRN_VEL_POWER`)과 신버전(`TRN_VEL`)이
  섞여 있고 세이브에는 신버전이 들어 있다 → **마이그레이션 필요**
- 검사: 데이터·화면·엔진이 같은 id 집합과 같은 수치를 쓰는지 (게이트)

### 3-2. 화면은 엔진을 그대로 보여준다

화면이 예상치를 **다시 계산하지 않는다.** 엔진에 미리보기를 묻는다.

```
growthPreviewNative({ protagonist, plan, efficiencyMod })
  → { fatigueDelta, conditionDelta, injuryRiskPct, statGains[] }
```

**실제 계산과 같은 코드를 탄다.** 그러면 슬롯 배수(1.0/0.5/0.5)와 피로 구간
승수가 자동으로 반영되고, 지금 같은 부호 역전이 구조적으로 불가능해진다.

### 3-3. 구종을 엔진에 넘긴다 ★루프를 닫는 축

**데이터는 이미 다 있다.** NPC 투수도 `roster_gen.rs`의 `gen_pitches`로
`{id, grade 1~5}` 배열을 갖는다 (패스트볼 등급은 구속이, 주무기 등급은 OVR이
정하고 에이스만 4% 확률로 너클볼). **엔진 입구에서만 끊긴다.**

```rust
pub struct SimPitcher {
    velocity, movement, command, control, stamina, clutch, mentality, hold_runners,
+   arsenal: Vec<PitchEntry>,   // { pitch_type, grade 1~5 }
}
```

`auto_pick_decision`을 **보유 구종에서 뽑도록** 바꾼다. 카운트 로직은 살린다:

```
볼 3개    → 스트라이크를 넣어야 한다. 제일 자신 있는 패스트볼 계열
스트라이크 2개 → 결정구. 숙련도 가중을 크게
그 외     → 보유 구종에서 숙련도 가중 추첨
보유 없음  → 패스트볼 폴백 (구 세이브·데이터 결손 대비)
```

**숙련도는 두 곳에 걸린다** (사용자 확정):

| | 효과 |
|---|---|
| 선택 빈도 | 숙련도가 높은 구종이 더 자주 나온다 → "주무기"가 저절로 생긴다 |
| 공의 품질 | `pitch_base(type) × grade_factor` → 헛스윙·약한 타구 확률 |

그러면 경기 로그가 **"결정구 슬라이더 헛스윙"**처럼 읽히고, 상대 에이스에게도
결정구가 생긴다.

⚠ **리그 전체의 득점 환경이 이동한다.** 지금은 모두가 Fastball/Slider/Changeup만
던지는 세계다. Phase 0에서 기준선을 잡고, 바꾼 뒤 다시 재서 비교한다
(`measure:batting` 등).

### 3-4. 폼 무너짐 ★시기 선택을 만드는 축

새 구종을 몸에 넣는 동안 **제구가 실제로 흔들린다.** 습득을 마치면 풀린다.

```
구종 개발 진행 중
  command −N · control −M  (임시. 원본 스탯은 안 건드린다)
  → 등판하면 ERA가 눈에 띄게 나빠진다
습득 완료
  임시 하락 해제 + 구종 획득
```

- **시즌 중에 배울까, 오프시즌까지 기다릴까**가 생긴다.
  성적이 걸린 해(드래프트 직전 3학년, FA 앞둔 시즌)에는 미루게 된다
- 하락 폭은 **구종 난이도와 현재 제구**로 정한다.
  너클볼은 크게, 체인지업은 작게. 제구가 좋은 투수는 덜 흔들린다

**⚠ 반드시 보이게 만든다.** 이 프로젝트는 "표시와 동작 불일치"로 이미 여러 번
당했다. 조용한 너프는 그중에서도 제일 나쁘다.

- 훈련 화면: `폼 교정 중 — 제구 −3 · 커맨드 −2 (남은 4주)`
- 내 정보 화면: 스탯 옆에 임시 보정 표시
- 소식: 습득 시작·완료 각 한 통
- **임시 하락이 `SimPitcher`까지 실제로 가야 한다.** 화면에만 적고 경기에
  안 가면 이번엔 반대 방향의 같은 결함이 된다

### 3-5. 죽은 것 처리

| 대상 | 처리 |
|---|---|
| `weekly_ratio_presets.json` | 삭제 (사용처 0, 지금 focus 체계와도 안 맞음) |
| 마스터의 `intensity` 필드 | `advanceWeek:316`의 별도 정의를 이걸로 대체하거나 삭제 |
| 카드의 `risk` 수치 | **실제 부상 판정에 물리거나 화면에서 뺀다.** 적혀 있는데 효과가 없는 게 제일 나쁘다 |
| `recoveryProgramId` | 제거. `SchedulePage`가 `secondary2ProgramId`를 읽게 |
| 타자 프로그램 | 마스터에 정본 신설 (지금은 화면 하드코딩만 있다) |

### 3-6. 끊긴 배선 복구

- **`focus` 조회** — 3-1의 id 통일이 끝나면 살아난다.
  살아난 **뒤에 다시 재서** 코치 관계·훈련 효율이 실제로 붙는지 확인한다
- **`ovrDelta: 0`** — `advanceWeek`가 관계 컨텍스트에 0을 박아 넘겨서
  감독 +1 · 코치 +2 성장 보너스가 죽어 있다. `growth` 결과가 같은 스코프에
  있으므로 배선은 한 줄이다. 다만 `growth_threshold: 2`가 주간 성장폭보다
  클 수 있으니 **배선 후 실측**해서 임계값을 정한다

### 3-7. 남은 밸런스 결정 (Phase 5에서)

- **슬롯 효율 역전** — 피로 1당 XP가 주 2.50 / 보조1 3.00 / 보조2 2.00이라
  "주 프로그램"이 최적이 아니다. 의도인지 확인 필요
- **29세까지 나이 계수 1.00** — 고교~프로 초반 성장 속도가 전부 같다.
  "고교 때 크게 크고 프로에서 완만해진다"를 원하면 지금 구조로는 안 나온다
- **잠재상한 감쇠**(0.95↑에서 0.10)가 충분한 벽인지

## 4. Phase

### Phase 0 — 계측과 게이트 ★반드시 선행

5. 게이트: 데이터·화면·엔진의 표가 어긋나면 실패하는 검사

### Phase 2 — 화면 = 엔진 (3-2)  ✅ 완료 (2026-08-08)

`previewTrainingNative` / `injuryChanceNative`. 둘 다 실제 계산과 **같은 함수**를
탄다 — `plan_load` · `injury_trigger_chance`.

실측 대조 (피로 62.125 · 제구/커맨드 + 구속 + 회복):

```
자동 −5.00 · 제구 3.0×1.0 +3.00 · 구속 5.5×0.5 +2.75 · 회복 −10×0.5 −5.00
= −4.25 → 57.875        화면 표시 58 ✓
```

예전 화면은 같은 상황에서 **+7**이라고 했다.

화면이 갖고 있던 자체 식 셋을 전부 없앴다. 그중 하나는 **엔진에 없는 보정**
이었다 — 코치·시설 계수로 피로를 깎았는데 엔진은 그런 걸 안 한다.

같이 정리된 것: `injury_trigger_chance`가 **세 곳에 복제**돼 있었다
(부상 판정 · 전조 경고의 `next` · 화면). 이제 하나다.

### Phase 3 — 구종을 엔진에 (3-3) ★가장 큰 변경

`SimPitcher.arsenal` → `auto_pick_decision` → 숙련도 가중·품질.
**Phase 0의 타격 기준선과 대조하며 조정한다.**

## 5. 규칙 (이 시스템을 건드릴 때)

- **표를 두 번 적지 않는다.** 이 시스템이 그걸로 망가졌다 — 네 곳이었다
- **화면이 엔진 공식을 다시 구현하지 않는다.** 엔진에 묻는다
- **적어놓은 수치는 효과가 있어야 한다.** `risk`처럼 표시만 있고 안 쓰이는 값을
  남기지 않는다
- **임시 보정은 화면과 경기 양쪽에 간다.** 한쪽만 가면 결함이다
- **수치를 바꾸면 잰다.** Phase 0의 기준선과 대조한다
