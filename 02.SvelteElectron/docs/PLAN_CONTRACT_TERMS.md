### 1-3. 재계약은 정말로 "금액·기간뿐"이다

`advanceWeek.ts:1306` 이 만드는 `salaryNegotiation`:

```

```

옵션·노트레이드·인센티브는 **아예 안 실린다.** 다만 협상 화면
(`ContractNegotiationModal.svelte`)이 주인공 쪽에서 셋을 **고를 수 있게** 열어

```

```

**즉 "구단이 조건을 제시한다"가 없다.** 조건은 주인공만 건다.

## §4 자료 구조 제안

### 4-1. `ProContract` — 두 칸만 는다

```ts
incentives?: {
  kind: "games" | "innings" | "era" | "wins" | "saves" | "holds" | "award";
  threshold: number;        // era 는 "이하", 나머지는 "이상"
  awardId?: string;         // kind === "award" 일 때만
  bonus: number;            // 만원
  paidSeasons?: number[];   // 정산한 해 — 두 번 주는 걸 막는다
}[];
buyout?: number;            // 1.1 · 지금은 안 쓴다
```

⚠ **`condition: string` 을 `kind` + `threshold` 로 바꾸자는 제안이다.**
지금 타입은 `{ condition: string; bonus: number }` 인데 문자열이라 **기계가
판정할 수 없다.** 값이 아직 없으니 지금이 바꾸기 제일 싼 때다.

### 4-2. 규칙 파일 키 — `generation_rules.json` 에 `contractRules` 를 새로

```jsonc
"contractRules": {
  "incentives": {
    "maxPerContract": 3,             // ✅ 확정 (상한 3)
    "totalPctOfSalary": 25,          // 제안 — 인센티브 총 최대가 연봉의 20~30%
    "perItemPctOfSalary": 15,        // 제안 — 항목 하나가 연봉의 15% 를 못 넘는다
    "byRole": {                      // ✅ 셋만 (스윙맨 없음) · 항목은 제안
      "SP": ["games", "innings", "era", "wins"],
      "RP": ["games", "holds", "era"],
      "CP": ["games", "saves", "era"]
    },
    "awardAxisAllRoles": true        // 수상은 보직과 무관하게 걸 수 있다 (제안)
  },
  "renewalSigningBonus": 0,          // ✅ 확정 — 재계약 계약금은 없다
  "counterOffer": {                  // ✅ 계수 확정 — 다만 횟수는 계산한다 (§5-2)
    "base": 1, "max": 3,
    "ratingBonusAt": 65, "ownerBonusAt": 30,
    "penaltyRatingBelow": 40, "penaltyOwnerBelow": 0
  }
}
```

**NPC 도 같은 구조를 쓰나 — 아니다(✅ 사용자 확정).** NPC 연봉은
`calc_npc_renewal_salary` 한 곳에서 나오고 인센티브를 정산할 자리가 없다.
NPC 에 붙이면 **매 시즌 수천 명의 정산**이 생긴다. 주인공만 쓰고, NPC
계약에는 `incentives` 를 안 넣는다. 1.1 뒤에 다시 본다.

**에이전트는 새로 안 만든다(✅ 사용자 확정).** 계약 소식의 보낸이가 이미
"에이전트"다(`contractDecision.ts:63`) — 사람이 아니라 **말투**로만 쓴다.

**옵션 행사 시점**: 지금 그대로 W39.
**인센티브 정산 시점**: 시즌 종료 처리(`runWorldSeasonEnd`)에서 **한 번**
(✅ 사용자 확정). 달성 즉시가 아니다 — 시즌 성적이 확정돼야 ERA·이닝을 셀 수 있다.

### 5-3. 인센티브 정산 — 어느 보직의 축으로 재나 (✅ 사용자 확정)

**계약할 때의 보직으로 조건을 고르고, 정산은 그 시즌의 보직으로 한다.**

```
계약 시점   그때 보직의 축에서 최대 3개를 고른다
정산 시점   다년 계약 중 보직이 바뀌면 **그 시즌 보직의 축**으로 잰다
            (3년 계약 2년차에 선발 → 마무리면 2년차는 마무리 축)
```

보직별 축 (✅ 셋만 · 스윙맨 없음 · 항목은 제안):

```
선발 SP   등판 · 이닝 · ERA · 승
중계 RP   등판 · 홀드 · ERA
마무리 CP 등판 · 세이브 · ERA
수상       보직과 무관하게 걸 수 있다 (제안)
```

⚠ **"그 시즌 보직" 이 정해지는 자리는 W1 이다.** `advanceWeek.ts:220` 의
`processWeekBoundary` 가 `weekNum === 1` 일 때 `assignProtagonistRole` 을 부르고
`gameStore.setPosition("SP" | "RP" | "CP")` 로 박는다. A 는 "시즌 시작 전 주"
라고 전했는데 **코드는 W1 이다** — 정산은 시즌 끝이라 어느 쪽이든 그 해 보직이
이미 정해져 있어 결과는 같다.

⚠ 보직이 바뀌면 **그 해에 못 잴 축이 생긴다**(선발로 계약했는데 마무리가 되면
"이닝 150" 은 사실상 도달 불가). 처리 갈래 둘 — **사용자에게 물을 것**:

```
① 못 잴 축은 그 해에 미달로 친다        간단하다 · 보직이 바뀌면 손해다
② 못 잴 축은 그 해 정산에서 뺀다        보직 변경이 벌이 안 된다 · 계산이 는다
```

지금 문서는 ②를 제안한다 — 보직을 바꾸는 건 구단이 정하는 일이라
주인공이 손해 볼 자리가 아니다.

### 5-2. 역제안 횟수 — 성적과 구단 애정도가 정한다 (✅ 사용자 확정)

**입력 둘 다 코드에 이미 있다. 새 필드를 안 만든다.**

```
성적    calcSeasonRating(stats)     salaryEngine.ts:34 → Rust
        advanceWeek.ts:1293 이 팀 옵션 행사 판정에 이미 쓴다(문턱 75 − 승부수/100×25)
애정도  Relationship { kind: "owner" }  relationship.ts:13
        그 줄의 주석이 **"재계약 · 방출 인내심"** 이다 — 이 자리를 위해 있는 축이다
        staffGen.ts 가 구단주를 만들고 game.ts:3538 이 관계를 굴린다 · 값 −100~+100
```

🔴 **주인공에게 `personality.loyalty` 는 없다.** `NpcPersonality.loyalty`
(`save.ts:855`)는 `NpcSaveState` 안에 있고 `ProtagonistSave` 에는 그 필드가
없다. 애정도를 `loyalty` 로 읽으려던 설계는 **여기서 막힌다** — `owner`
관계가 대신이다.

규칙 (✅ 계수 넷 사용자 확정 2026-09-03 — 그대로 간다):

```
rounds = 1
      + (seasonRating >= 65 ? 1 : 0)        잘한 해엔 한 번 더 부른다
      + (ownerRelation >= 30 ? 1 : 0)       구단주가 아끼면 한 번 더
      − (seasonRating < 40 && ownerRelation < 0 ? 1 : 0)   둘 다 나쁘면 한 번뿐

      clamp 1 ~ 3
```

⚠ **관계 값을 화면에 숫자로 쓰지 않는다.** `relationship.ts:44` 가
"플레이어에게 숫자로 노출하지 않는다 — 라벨만 보여준다"고 못박아 뒀다.
화면에는 남은 횟수만 보인다(`역제안 2회 남음`).

⚠ 구단주 관계가 **없는 경우**(스태프가 아직 안 붙은 팀)는 0 으로 본다 —
그러면 성적만으로 1~2회가 된다.

### 7-1. 🔴 인센티브 문턱을 어떻게 재나 (사용자: "제안값은 두되 확정 전에 잰다")

**문턱을 정하기 전에 분포부터 본다.** 지금 제안값(25등판·150이닝·ERA 3.00·10승)은
실측 근거가 하나도 없다 — KBO 감각으로 적은 숫자다.

```
무엇을     주인공의 시즌별 등판·이닝·ERA·승 분포 (프로 무대만)
어떻게     scripts/perf/perfEntry.ts 의 protagonistStatProbe() 가 이미
           경기·ip·era·whip·"N승 M패 S세이브 H홀드" 를 낸다 — 새 계기가 필요 없다
어디서     measure:slotreach 와 같은 하네스로 --path draft · 12시즌 · 씨앗 3
           시즌이 끝날 때마다 그 값을 한 줄씩 찍는 probe 를 하나 붙인다
보는 값    문턱별 달성률 — "25등판을 몇 %의 시즌이 넘나"
```

판정 기준(제안): **한 문턱의 달성률이 20~50%** 면 쓸 만하다.
80% 를 넘으면 공짜고, 5% 아래면 안 걸린 것과 같다.

⚠ 보직으로 갈린다 — 선발과 마무리는 등판·이닝 분포가 아예 다르다.
`byRole` 표(§4-2)를 그래서 뒀고, **분포도 보직별로 따로 봐야 한다.**

⚠ 이 계측은 **밸런스 확정용이지 1.0 출시 조건이 아니다.** 프리즈(9/15) 안에
못 재면 제안값으로 내고 1.1 에서 고친다 — 그때는 실제 플레이 기록이 근거가 된다.

### ✅ 남은 셋도 답을 받았다 (2026-09-03 · A 전달)

| 물은 것 | 답 |
|---|---|
| 역제안 계수 넷 (65 · 30 · 40 · 0) | **그대로 간다** |
| 인센티브 개수·금액 | 개수 상한 **3 유지** · 총 최대 연봉의 **20~30%** · 항목당 **15%** (제안) |

**금액 비율의 근거** — A 가 전한 KBO 통상: FA 계약은 계약금+연봉+옵션 구조이고
옵션(인센티브) 몫이 총액의 **대략 10~30%**(부상 이력·베테랑은 더 큼), 조건 수는
보통 **2~5개**(출전·이닝·타석, 성적, 수상, 팀 성적)이며 대개 비공개다.

🔴 **이건 일반 지식이지 실측이 아니다.** 이 게임의 연봉 규모(`salaryRules`)로
같은 비율이 맞는지는 안 쟀다 — §7-1 계측에서 문턱과 같이 본다.
