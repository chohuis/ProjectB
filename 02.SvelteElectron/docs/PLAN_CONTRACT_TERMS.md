# 주인공 계약 조건 — 기획안 (2026-09-03 · 트랙 B)

> **기획만이다. 코드·Rust·데이터를 하나도 안 고쳤다.**
> 숫자는 전부 코드·규칙 파일에서 읽은 것이고, 아닌 것은 **추측**이라 적었다.
> 밸런스 값은 전부 **제안**이며 사용자 확정 전에는 넣지 않는다.
> 사용자에게 물을 것은 §8 에 번호로 모았다.

### 1-2. 엔진은 이미 조건을 낸다 — 화면이 안 보여 줄 뿐

`team_engine.rs:656` `eval_fa_bid` 가 내는 것:

```
bid_salary        시장가 × (1+스카우팅 잡음) × 승부수 배수 · 상한은 여유예산 · 바닥 1500
bid_years         안정성 > 65 → 요구연수(최대 4) · < 35 → 요구−1 · 그 사이 → 요구 그대로
```

`faEngine.ts:360` `toContract` 가 이 넷을 그대로 계약에 옮긴다.
그런데 **`FaMarketModal.svelte` 의 제안 카드는 `연봉 / 기간` 두 줄뿐**이다 —
계약금도 옵션도 노트레이드도 **고르기 전에는 안 보인다.** 서명하고 나서
선수 상세에서야 보인다.

### 1-3. 재계약은 정말로 "금액·기간뿐"이다

`advanceWeek.ts:1306` 이 만드는 `salaryNegotiation`:

```
offeredSalary   calcOfferedSalaryForProtagonist 가 낸다
durationYears   1        (min 1 · max 3)
signingBonus    **0 고정**
```

옵션·노트레이드·인센티브는 **아예 안 실린다.** 다만 협상 화면
(`ContractNegotiationModal.svelte`)이 주인공 쪽에서 셋을 **고를 수 있게** 열어
두고, 수락 확률을 이렇게 깎는다:

```
노트레이드 요구      × 0.95
팀 옵션 1년 / 2년    × 1.05 / × 1.10   (구단에 유리하니 확률이 오른다)
선수 옵션 1년 / 2년  × 0.97 / × 0.94
연봉 요구            슬라이더 ±20%
```

**즉 "구단이 조건을 제시한다"가 없다.** 조건은 주인공만 건다.

## §4 자료 구조 제안

### 4-1. `ProContract` — 두 칸만 는다

```ts
incentives?: {
  kind: "games" | "innings" | "era" | "wins" | "saves" | "holds" | "award";
  threshold: number;        // era 는 "이하", 나머지는 "이상"
  awardId?: string;         // kind === "award" 일 때만
  bonus: number;            // 만원
  paidSeasons?: number[];   // 정산한 해 — 두 번 주는 걸 막는다
}[];
buyout?: number;            // 1.1 · 지금은 안 쓴다
```

⚠ **`condition: string` 을 `kind` + `threshold` 로 바꾸자는 제안이다.**
지금 타입은 `{ condition: string; bonus: number }` 인데 문자열이라 **기계가
판정할 수 없다.** 값이 아직 없으니 지금이 바꾸기 제일 싼 때다.

### 4-2. 규칙 파일 키 — `generation_rules.json` 에 `contractRules` 를 새로

```jsonc
"contractRules": {
  "incentives": {
    "maxPerContract": 3,          // 제안
    "byRole": {                    // 보직마다 걸 수 있는 축이 다르다
      "SP": ["games", "innings", "era", "wins", "award"],
      "RP": ["games", "holds", "era", "award"],
      "CP": ["games", "saves", "era", "award"]
    },
    "bonusPctOfSalary": { "easy": 5, "normal": 12, "hard": 25 }  // 제안
  },
  "renewalSigningBonusPct": 0,     // 제안 — §8 Q2
  "counterOffer": { "maxRounds": 2 }  // 제안 — §8 Q4
}
```

**NPC 도 같은 구조를 쓰나 — 아니다(제안).** NPC 연봉은
`calc_npc_renewal_salary` 한 곳에서 나오고 인센티브를 정산할 자리가 없다.
NPC 에 붙이면 **매 시즌 수천 명의 정산**이 생긴다. 주인공만 쓰고, NPC
계약에는 `incentives` 를 안 넣는다.

## §5 협상 흐름

```
W39  계약 만료 판정 (지금 그대로)
  ├─ 팀 옵션 있음   → OptionClauseModal  (구단이 행사 여부를 이미 정해 온다)
  ├─ 선수 옵션 있음 → OptionClauseModal  (주인공이 고른다)
  ├─ FA 자격        → FaMarketModal      ← **여기 카드에 조건을 다 보여 준다**
  └─ 그 외          → ContractNegotiationModal ← **여기에 구단 제시 조건을 싣는다**

협상 한 판 (제안)
  ① 구단 제시    연봉·기간·계약금·옵션·인센티브 후보
  ② 주인공 역제안  연봉 ±20%(지금 있는 슬라이더) · 기간 · 조항 · 인센티브 고르기
  ③ 구단 판정    지금의 수락 확률 식에 인센티브 항을 더한다
  ④ 수락 / 거절 / 재역제안(최대 N회 — §8 Q4)
```

**에이전트는 새로 안 만든다(제안).** 계약 소식의 보낸이가 이미 "에이전트"다
(`contractDecision.ts:63`) — 사람이 아니라 **말투**로만 쓴다. 에이전트를
능력치 있는 존재로 만들면 협상 결과에 곱이 하나 더 붙어 밸런스가 흔들린다.

**옵션 행사 시점**: 지금 그대로 W39. **인센티브 정산 시점**: 시즌 종료 처리
(`runWorldSeasonEnd`)에서 한 번 — §8 Q3.

## §8 🔴 사용자에게 물을 것

1. **인센티브를 넣나?** 계약 조건 중 유일하게 새로 만드는 항목이다. 나머지
   넷(계약금·옵션 표시·노트레이드 표시·최저연봉)은 이미 있는 걸 잇는 일이라
   싸다. 인센티브만 정산 구조가 새로 필요하다.
2. **재계약에도 계약금을 주나?** 지금은 FA·신인만 준다(재계약 0 고정).
   KBO 에선 재계약에 계약금이 흔치 않다 — 0 을 그대로 둘지, 연봉의 몇 %를 줄지.
3. **인센티브 정산은 시즌 끝 한 번인가?** 아니면 달성 즉시인가.
   시즌 끝 한 번이 싸고, 즉시가 체감이 크다.
4. **역제안을 몇 번까지 하나?** 지금은 한 번(수락/거절)이다. 2~3회로 늘리면
   협상 맛이 나지만 거절 위험이 커진다.
5. **NPC 계약에도 같은 조건을 주나?** 제안은 **안 준다**이다(수천 명 정산이
   생긴다). 주인공만 특별한 게 어색하면 말해 달라.
6. **최저연봉을 협상 하한으로 물리나?** 지금 슬라이더는 −20% 인데 그게
   3000만원 아래로 내려갈 수 있다(계산상). 규칙 파일 값으로 막을지.
7. **에이전트를 사람으로 만드나?** 제안은 **아니다**(말투로만). 능력치 있는
   에이전트를 두면 협상에 곱이 하나 더 붙는다.
8. **인센티브 문턱 난이도** — 예: 선발 25등판 / 150이닝 / ERA 3.00 이하 /
   10승. 이 값들은 **전부 제안이고 실측 근거가 없다.** 확정 전에 잰다.
9. **바이아웃·연봉조정·옵트아웃은 1.1 로 미루는 게 맞나?** 셋 다 재정·시장
   구조를 건드린다.
