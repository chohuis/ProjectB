### 팀 색 규칙 — 이게 이 디자인의 전부다

`utils/teamTheme.ts`가 팀 색 하나에서 화면 토큰을 만든다. **컴포넌트가 각자
팀 색을 읽으면 이적 한 번에 52개 화면을 고쳐야 한다** — CSS 변수를 문서
루트에 두는 이유다.

    --t-dark    헤더·사이드바·표 머리선   주색을 L*26으로 낮춘 값
    --t-accent  CTA·경고                 refs.json 보조색 그대로
    --t-gold    어두운 바탕 위 강조        주색을 L*72로 올린 값
    --t-stripe  핀스트라이프              주색 5.5% 투명

⚠ **주색을 헤더에 그대로 쓰면 안 된다.** 238팀 주색 L* 13~83이고 130팀(55%)이
L* > 45다 — 광주 팬서스(#F49530, L*70)는 흰 글씨가 죽는다.

⚠ **골드를 회색과 섞으면 안 된다.** 채도 높은 색은 배율만으로 L*72에 못 닿아
보정이 필요한데, 회색과 섞으면 명도는 맞고 **색조가 죽는다** — 부산·대전·서울
로열스가 전부 `#B0B0B0`이 됐다. 흰색과 섞어 틴트로 만든다.

⚠ **판정은 L* 수치가 아니라 대비다.** 골드를 "L*72 이상"으로 봤더니 L*58짜리가
통과했는데 헤더 위에서 대비 3.2:1이라 안 읽혔다. 헤더와의 대비 4.5:1로 본다.

### 통산 요약은 슬롯 메타에 있다

**스키마 변경이 아니다**(마이그레이션 불필요).

⚠ **통산 ERA는 시즌 ERA의 평균이 아니다.** 자책 합 × 9 ÷ 이닝 합이다. 평균이면
5이닝 시즌과 180이닝 시즌이 같은 무게라 데뷔·부상 한 시즌이 통산을 흔든다

```
[시점] KBL_1군  오프시즌직후 야수12/투수5  →  시즌종료 야수7/투수7
```

직전 측정에선 투수 9~11명이었는데 **5명**이 됐다. 야수를 지키려다 투수를
무너뜨린 것이다.

고친 내용:

- `tuning.rs`에 `FIRST_TEAM_MIN_PITCHERS`(12) 추가 — 근거는 야수 하한과 같은 축
  (`rosterSize` 30 × `pitcherRatio` 0.45 = 투수 14 / 야수 16, KBO 1군 투수 11~13)
- `eval_calldown_candidates`(team_engine.rs) — 양쪽 하한을 다 보고,
  **둘 다 하한 이하면 강등을 멈춘다.** 그 상태는 강등으로 풀 문제가 아니다
- `fill_first_teams`(npc_sim.rs) — 야수 자리 만들려고 투수를 내리는 경로에도
  같은 하한. 이쪽을 빼먹으면 오프시즌에 같은 일이 다시 벌어진다
- `cargo test`에 판정 직접 호출 5건 추가 (147개) — **이건 통계 감사로는 못 잡는다.**
  집계만 보면 "야수 7명"이 강등 때문인지 콜업 편중 때문인지 구분이 안 된다

### 검사 기준을 세 단계로 나눴다 (2-g)

`test-roster-balance.cjs`가 "포수 0명"과 "좌익수 공백"을 똑같이 FAIL 한 줄로
냈다. 이 모델의 수비는 `fielding` 단일 스탯이라 **포지션 배치가 경기 결과에
안 들어간다** — 좌익수 공백은 표기 문제고, 야수 9명 미만은 타순이 짧아져
성적이 능력치가 아니라 출전량으로 결정되는 **다른 종류의 문제**다.

| 단계 | 대상 | 기준 |
|---|---|---|
| 치명 | 야수<9 · 포수 0명 | 한 팀도 허용 안 함 |
| 하한 | 구성 하한 미달 | 미달 **비율** 5% 초과면 실패 |
| 경고 | 포수 외 포지션 공백 | 보고만 함 |

**하한을 최소값으로 보면 안 된다.** 최소는 (팀 수 × 시즌 수) 표본의 극단값이다.
`rosterCompositionProbe`가 분포·5퍼센타일·타순미달팀을 같이 낸다.

### 하한값 자체가 틀렸다 (2-h — 결함이 아니었다)

비율 기준으로 바꾸자마자 **고교 102팀 전부**가 야수 하한 미달로 나왔다.
전 팀이 미달이면 대개 기준이 틀린 것이다 — 실제로 그랬다.

야수 하한 11은 `rosterSize`(30)에서 뽑은 값인데, **고교는 학년제라 졸업 직후
로스터가 `rosterMin`(18)까지 내려간다.** 18 × 야수비율 0.55 = 9.9이니
야수 9~10은 정상이다. 시점 대조도 오프시즌직후 9 → 시즌종료 10으로 **늘어난다** —
유출이 없다. 하마터면 멀쩡한 생성 경로를 파고들 뻔했다.

이제 하한을 **규칙 파일에서 파생한다** (`rosterMin` × 보직비율 − 여유 2):

| 리그 | rosterMin | 야수 | 투수 |
|---|---|---|---|
| 고교 · 독립 | 18 | 7 | 6 |
| 대학 | 20 | 9 | 7 |
| KBL 1군 · 2군 | 26 | 12 | 9 |

### 시즌 중 야수 유출 = 트레이드였다

시점 대조가 KBL 1군에서 **야수만** 빠지는 걸 보여줬다(오프시즌 11~13 → 시즌종료 8).
콜다운은 이미 막았고 콜업은 `a.position == farm.position`이라 1:1이다. 원인은
**트레이드가 보직을 안 본 것**이다 — 네 유형 전부 부류를 넘나들고, 부상 보강은
아예 `pl.position != inj_pos`인 선수를 내준다. 투수 수요가 더 크니 야수가
한 방향으로 샜다.

`generate_trade_proposals` 끝에서 **제안 목록 전체를 한 번에 거른다.** 생성 지점
네 군데에 각각 걸면 다섯 번째 유형이 생길 때 또 빠진다.

### ⚠ 로스터 측정은 한 번 돌려서 판단하면 안 된다

같은 시드·같은 바이너리인데 KBL 2군 투수 최소가 **6 ↔ 4**로 흔들린다.
주간 시뮬이 `thread_rng()`라 재현되지 않는다(설계상 의도). 로스터 수치를
고칠 때는 **여러 번 돌려 방향을 보고**, 한 번의 개선/악화를 결론으로 삼지 않는다.

### 포수 0명은 유출이 아니라 **회복 경로가 없던 것**이었다

트레이드로 유출을 막아도 리그마다 1~2팀이 포수 0명으로 남았다. 원인은
**콜업이 같은 포지션 1:1 교체**라는 것이다 — 포수가 0명이면 `active_at_pos`가
비어 `continue`로 건너뛰고, 2군 포수를 올릴 방법 자체가 없다.
메워주는 `fix_position_gaps`는 오프시즌에만 돈다.

`eval_callup_candidates`에 공백 충원(`position_gap`)을 넣었다 — 자리가 비면
같은 부류의 남는 자리에서 최약체를 내리고 채운다. 상시 경로에도 포함시켰다
(포수 0명인 팀을 월간 주기까지 기다리게 할 수 없다).

그랬더니 **2군 투수가 7 → 0명**이 됐다. 일반 콜업은 부류를 안 바꾸는데
공백 충원만 넘나들기 때문이다. `FARM_MIN_PITCHERS`(8)·`FARM_MIN_BATTERS`(9)로
막았다.

### 남은 것은 전부 **공급 부족**이다 (유출은 다 막았다)

| | 내용 | 실측 |
|---|---|---|
| **2-i** | KBL 2군 투수 | 5~7명 (하한 9). 2/10팀 미달 |
| **2-j** | 고교 투수 | 4~5명 (하한 6). **21/102팀** 미달 |
| **2-k** | 2군 포수 0명 | 2팀. 2군은 콜업의 **공급원**이라 자기 공백을 메울 경로가 없다 |

성격이 앞의 것들과 다르다. 하한을 더 걸어봐야 이번엔 반대편이 막힐 뿐이고
(2군 하한을 걸면 1군 공백이 안 메워진다), **없는 사람을 만들어야 한다** —
육성선수 생성이 후보다.

### 신입생 자리 배정 — 폴백에 비율을 맡기면 안 된다 (해결)

`neededPositions`를 **두 번 반대로 틀렸고**, 그때마다 10분짜리 세계 시뮬로
확인했다. 순수 함수인데 그렇게 검증하고 있었다 — 이제
`npm run test:neededpositions`가 즉시 잡는다.

| | 한 것 | 결과 |
|---|---|---|
| 1차 | 백업 자리(전부 야수)로 남은 칸을 다 채움 | **투수 15.8%**(목표 45%). 지정 613칸이 전부 야수였다 |
| 2차 | 백업을 아예 뺌 | **포수 0명 8~11팀.** `empty`는 자리가 0이 된 뒤에야 도는데 백업이 그 전에 채우는 장치였다 |
| 3차 | 지정 리스트가 비율을 직접 지킴 | 포수 0명 0팀 · 투수 미달 0팀 · 타순 미달 12~14 → 3~4팀 |

**폴백(난수)에 비율을 맡기는 것 자체가 틀렸다.** 난수는 팀별 편차를 만들고,
그게 포수 0명·투수 부족의 원인이었다. 최종 우선순위:

```
① 빈 야수 자리(포수 먼저)   ② 야수 총원<9 ┐ 둘 다 모자라면 비례 배분
                            ③ 투수 하한   ┘
④ 남은 칸 — 투수 비율(0.45)대로 투수와 백업 자리를 섞는다
```

곁들여 **생성 시드가 `school_id.len()`이었다** — 같은 길이 학교가 같은 난수열을
쓴다. 102팀에 길이는 몇 종류뿐이라 충돌이 심했다(폴백만 도는 해에 투수 비율이
목표 45%인데 32.5%). 글자 값을 섞도록 고쳤다.

남은 것: 고교 타순 미달 3~4팀, KBL 1군 야수 12 미달 2/10팀.

### (해결됨) 고교는 배분이 아니라 총원이 부족하다 — **오판이었다**

최소값 12~13명을 보고 "총원 부족"이라 결론냈는데, 실측하니 **생성은 요청대로
100%**(요청 1,020 → 생성 1,020)였다. 최소는 102팀의 극단값이다 —
2-h에서 같은 실수를 하고도 또 했다. 진짜 원인은 위의 배정 로직이었다.

```
고교 시점: 야수 7 / 투수 5~6 = 총 12~13명      rosterMin = 18
```

팀 총원이 최소 정원에도 한참 못 미친다. **배분을 어떻게 바꿔도 없는 인원은
나눌 수 없다** — `neededPositions`에 야수 총원 하한을 넣었더니 타순 미달이
20 → 22팀으로 오히려 늘었다.

투수 폴백 비율 수정이 만든 문제가 아니다. 그전엔 투수가 적어 야수가 상대적으로
많아 보였을 뿐이고, 총원 부족은 원래 있었다.

다음에 볼 것: `generateFreshmenV3`의 `want = min(perYear, rosterSize − 현재)`가
실제로 몇 명을 만드는지. 문서에 "생성이 요청량을 못 채워 1학년이 절반만
들어온다(실측 507/1,020)"는 기록이 있고 고쳤다고 되어 있는데, 총원을 보면
여전히 모자란다. **요청량과 실제 생성량을 먼저 찍을 것** — 이번에 육성선수에서
같은 실수를 했다(효과부터 재고 생성량을 안 봤다).

### 투수 총량 — 신입생 폴백이 30%였다 (해결)

육성선수(2군 보직 하한 충원)를 넣어 포수 0명·타순 미달은 해소됐지만
**투수 부족은 안 풀렸다.** 원인이 더 위에 있다:

```
1군 투수 6~8  +  2군 투수 5  =  11~13     하한 합 = 21
```

구단당 투수 총량이 절반 수준이다. 2군에 4명 만들어도 시즌 중 1군이 다
끌어올린다 — **1군도 부족하기 때문**이다. 야수는 2군에 18~20명으로 남아돈다.

**고교 투수도 23/102팀 미달**이다. 파이프라인 최상류부터 모자라니 대학·독립·
드래프트를 거쳐 프로까지 계속 부족하다. 육성선수 4명/년으로 메울 규모가 아니다.

유력한 원인은 `neededPositions`의 우선순위다 — ①빈 야수 자리 ②투수 ③백업 없는
야수 자리 순이라 **모든 충원 경로가 야수로 기운다.** 투수 몫을 먼저 떼도록
고쳤지만(cebc9b9c3) `count`가 작으면 여전히 야수가 먼저 먹는다.

**원인은 신입생 생성의 무작위 폴백이었다.** 로스터 생성은 `pitcher_ratio`(0.45)로
만드는데 `generate_freshmen`의 폴백은 `rng < 0.3`이 박혀 있었다 — 세대가
교체될수록 리그가 30%로 수렴한다(30명 로스터 기준 투수 13.5 → 9명).

고치자 **세 리그가 함께** 좋아졌다. 한 리그만 좋아졌다면 원인이 다른 데
있다는 뜻이었을 것이다:

| | 이전 | 이후 |
|---|---|---|
| 고교 투수 미달 | 23/102팀 | ≤5팀 |
| KBL 1군 투수 | 6~8 | 9~10 |
| KBL 2군 투수 | 5 | 6~8 |

⚠ 그리고 예상대로 **반대편이 밀렸다** — 고교 타순 미달이 0 → 20팀.
`neededPositions`가 포지션 공백만 보고 **야수 총원을 안 봤다**(8자리 중 7자리가
차 있으면 공백은 1개뿐이다). 총원 하한을 ②순위로 넣었다 — 타순 한 바퀴는
경기 성립 조건이라 투수 하한보다 앞이다.

### 육성선수를 정원으로 막으면 한 명도 안 만들어진다

`room = rosterMax − 총원`을 여유로 뒀는데 **W1의 2군은 총원이 꽉 차 있다**
(투수 6 / 야수 28처럼 총원은 맞고 보직이 틀린 상태다). 그래서 `want`가 항상 0이었고
실측이 그대로였다 — 이 작업 내내 잡아온 "몇 명은 맞는데 어느 자리가 틀렸다"를
그대로 재현했다.

육성선수는 **정원 밖 인원**이다(실제 KBO도 정식 등록 외로 뽑는다).
정원 초과분은 오프시즌 캡이 남아도는 부류부터 정리하면서 저절로 맞고,
폭주는 `maxPerYear`가 막는다.

⚠ **"효과가 없다"에서 "안 도는 건지 모자란 건지"를 가르는 데 세 번 돌렸다.**
`autoLog`는 `setLogFile`을 안 부른 스크립트에서 버려지고, 조건부 로그는
그 조건이 거짓이면 안 찍힌다. **효과 측정 전에 "실제로 몇 개 만들었나"를
무조건 찍어야 한다.**

### OVR–성적 상관 — 원인은 **자(尺)가 부러진 것**이었다 (2026-08-04)

"시즌이 갈수록 능력치가 성적을 못 만든다"를 쫓아 가설 여섯 개를 세웠고
**여섯 개가 전부 측정으로 반증됐다.** 진범은 목록에 없던 측정 도구였다.

```ts
// abilitySpreadProbe — 이 한 줄이 표본을 결과값으로 잘랐다
if (n.currentLeague !== leagueId || ...) continue;
```

`LEAGUE_KBL_FARM`은 별도 리그 ID다. 그래서 **그 시즌 1군에서 100이닝을
던지고 부진해서 강등된 투수가 통째로 빠진다.** 강등은 성적이 나빠서
당하니 나쁜 ERA만 골라 지운 셈이고, 승강이 활발해지는 후반 시즌일수록
더 많이 지워진다 — 상관이 해마다 무너지는 모양이 정확히 이것이었다.

| | 이전 | 이후 |
|---|---|---|
| 합산 | −0.172 | **−0.322** |
| 선발만 | −0.207 | **−0.401** |
| 2030 선발 | −0.11 | −0.45 (표본 83 → 185) |

**선발 −0.4는 정상이다** (실제 야구의 한 시즌 ERA–실력 상관이 −0.4~−0.5).
시즌별 단조 감쇠도 사라졌다. **소속 리그가 아니라 그 리그의 기록 버킷이
정본이다** — 기록이 있으면 그 리그에서 던진 것이다.

반증된 가설: 불펜 희석 · 선발 과잉 · OVR 공식과 경기의 괴리 · 범위 제한 ·
타순 미달 팀 · 제구 천장 포화. 마지막 둘은 실제로 존재하지만(천장에 9%가
붙어 있고 타순 미달도 간헐적으로 난다) **감쇠의 원인은 아니었다.**

### 성격 계수 — 계수는 맞았고, 안 보이는 게 문제였다 (2026-08-04)

`npc_clutch_mod`의 계수를 실측했다. **조정할 근거가 없었다:**

| | 배율 | 타율 | 중립 대비 |
|---|---|---|---|
| 중립 | 1.000 | .227 | — |
| 득점권 | 0.945 | .229 | +.003 |
| 최악(만루2아웃9회1점차) | 0.853 | .233 | +.006 |

**실제 MLB 통산 득점권 차이가 +.002다.** 방향도 폭도 맞는다. 효과가 주로
볼넷으로 나오는 것도 확인했다(출루−타율 간격 .050 → .072) — 제구·커맨드를
깎으니 안타보다 볼넷이 먼저 늘어난다.

문제는 **성격이 기록에 안 보인다**는 것이었다:

    기질 20 (배율 0.800)  피안타율 .235
    기질 90 (배율 0.924)  피안타율 .229   차 .006

득점권은 전체 타석의 22~24%뿐이라 시즌 성적으로 희석되면 ERA 0.18 차이고,
**ERA 노이즈가 ±0.14다. 신호와 잡음이 비슷하다.**

계수를 키우면 상황이 능력치를 압도한다 — 바로 위에서 15시즌 걸려 고친 게
그 방향이다. 그래서 **계수는 두고 득점권 스플릿을 기록에 남겼다**(사용자 확정).
실제 야구도 이걸 시즌 ERA가 아니라 상황별 성적으로 본다.

실측(리그 3시즌): 타석비중 22~24%(실제 20~28%) · 득점권 차이 평균 −.001 ·
투타 대사 일치. `PlayerSeasonStats.rispAb/rispH`에 쌓인다.

⚠ **UI 표시는 아직 없다.** 데이터만 있다 — 어느 화면에 보여줄지는 미결.

⚠ **엔진 검사만으로는 모자랐다.** `득점권_기록이_쌓인다`는 `sim_game`만 본다.
그 값이 TS 누적을 거쳐 시즌 기록에 남는지는 별개고, 이 프로젝트에서 세이브·
도루가 정확히 그 층에서 0이었다. `rispSplitProbe`를 따로 둔 이유다.

### 리그가 해마다 얇아지던 것 — 해결 (2026-08-04)

원인은 **한 줄**이었다. `generate_freshmen`이 `potential_hidden`을
`ovr_max * 1.15` **고정값**으로 줬다 — 난수가 없어 고교 신입생 1,020명이
매년 전원 80.5로 같은 천장을 가졌다. **파이프라인 전체에 재능 편차가
없으니 새 에이스가 안 나온다.** 창단 KBL 세대(88 × 1.05~1.25 = 92~99)가
은퇴하면 그 자리를 아무도 못 채웠고, 실측 천장 82가 고정값 80.5와 거의 같다.

고친 방향은 **재능 상위 꼬리**다(사용자 확정) — 대부분의 성장 속도는
그대로 두고 소수(3%)만 천장과 속도를 함께 받아 에이스로 자란다. 성장
곡선 전체를 올리는 것과 달리 주인공 체감·은퇴 시점·FA 가치를 안 건드린다.
정본은 `generation_rules.json`의 `talentRules`이고 **세 생성 경로가
`tuning::sample_talent` 하나를 공유한다**(초기 세계·매년 신입생·용병).

이어서 창단 대역을 88 → 84로 낮췄다(사용자 확정). 정상 상태가 84인데
창단만 90이라 첫 4시즌 동안 리그가 약해지는 것처럼 보였고, **창단 90
쪽이 인위적이었다** — 프로를 전성기 대역에서 직접 생성했고 전원이
잠재력 92~99였다(90이상 57.2%, 파이프라인은 3%).

실측 15시즌 (상위25% OVR):

| | 수정 전 | 수정 후 |
|---|---|---|
| 창단 2026 | 89.9 | **86.1** |
| 정상 2041 | 83.4 | 82.8 |
| 하락 폭 | 6.5점 | **3.3점** |

정상 상태는 그대로고 창단만 내려왔다 — 대역 조정이 파이프라인에 영향을
주지 않았다는 뜻이다. 2030년부터 82.6~84.1로 평평하다.

**선발 OVR-ERA 합산 15시즌 −0.33 ~ −0.38** (표본 1,400명). 2029년 이후
12시즌 동안 −0.24~−0.41에서 안정 — 실제 야구의 한 시즌 ERA–실력 상관
(−0.4~−0.5)과 같은 범위다. **A는 닫혔다.**

⚠ **이 수정은 6시즌 측정으로 평가할 수 없다.** 2026년에 태어난 꼬리는
16~18세라 6시즌 뒤에도 22~24세다 — 효과가 1군 상위권에 도착하려면
10~15년이 걸린다. 실제로 6시즌 측정은 82.58로 거의 그대로였고,
**거기서 "효과 없음"으로 되돌릴 뻔했다.** 그래서 `potentialProbe`를
따로 만들었다 — "효과가 도착했는가"가 아니라 **"씨앗이 뿌려졌는가"**를 본다.

### (이전 기록) 리그가 해마다 얇아진다

같은 측정에서 나온 별개 문제다. 세 번의 독립 실행에서 전부 같았다:

```
OVR 상위25%   89.3 → 82.1     ← 에이스가 사라진다
OVR 하위25%   67.3 → 71.4     ← 밑은 올라온다
분산            22.0 → 10.7    ← 6시즌에 절반
리그 ERA         4.0 →  5.6
```

**초기 생성은 85~90짜리 에이스를 깔지만 성장 엔진은 그걸 다시 못 만든다.**
성장 실측이 25~27세 +1.45/시즌, 28~30세 +0.36인데 드래프트 신인은
60~70에서 시작한다 — 85에 닿기 전에 전성기가 끝난다. 처음 깔아둔
에이스가 은퇴하면 그 자리를 아무도 못 채운다.

20시즌을 미는 게임에서 **플레이어가 성장할수록 리그가 쉬워지고 후반
기록이 전부 부풀려진다.** 성격 계수(클러치) 조정은 여기에 막혀 있다 —
능력 분포 자체가 6시즌에 절반으로 좁아지면, 초반에 맞춘 계수가 후반에
안 맞는다.

### NPC 생애 추적이 잡은 것 — 집계로는 안 보이는 층

`npm run test:npclifecycle` (신설). 표시한 111명을 여러 시즌 따라간다.

**20시즌 병역 장부에서 상무 이력 소실을 찾았다:**

```
고치기 전  2026~2044 상무  0 · 현역 43     ← 19년치가 현역으로 집계
고친 후    2027~2036 상무 13 · 현역 30     ← 정원(26÷2년) 정확
```

입대 자체는 내내 정상이었고 **분류만 사라지고 있었다** — 전역 처리가
`military_unit`을 지웠기 때문이다. `military_served_unit`으로 남긴다.

⚠ **첫 실행에서는 검사 전제가 세 번 틀려 없는 결함을 만들어냈다**
(복무 중 소속·나이 +1·연도 연속). 전부 커밋 전에 되돌렸다 —
**검사가 관측 못 한 것과 일어나지 않은 것은 다르다.**

### ⚠ OVR–ERA 상관이 시즌이 갈수록 무너진다 (원인 좁혀짐, 미해결)

```
2026  선발 61명 → −0.63       2030  선발 86명 → −0.18
2027  선발 58명 → −0.52       2031  선발 90명 → −0.30
2029  선발 71명 → −0.29       2032  선발 96명 → **+0.12**
```

**선발 수가 늘수록 상관이 약해진다.** 2032는 양수까지 갔다.

가설 두 개를 실측으로 걷어냈다:

- **"불펜이 섞여서"** — 아니다. 불펜은 표본이 1~12명뿐이고 전체의 90%가 선발이다
- **"충원이 선발을 많이 뽑아서"** — 일부만 맞다. 세 경로의 선발 비중이
  45%(생성) / 55%(신입생 폴백) / **67%**(`neededPositions`)로 갈려 있어
  `SP_SHARE_OF_PITCHERS`로 통일했는데, 그래도 61 → 96으로 늘었다

**남은 원인: 로테이션이 매 경기 재선정된다.**

`getTeamRotation`은 `maxRotation` 5로 제한하지만, **휴식 완료된 SP를
`effectiveOvr` 순으로 매번 다시 뽑는다.** 컨디션이 흔들리면 상위 5명 집합이
계속 바뀌어, 팀에 SP가 12명이면 12명이 돌아가며 던진다 — 각자 7~12번뿐이다.

실제 야구는 로테이션이 **고정**이고 5명이 각자 28번 던진다. 표본이 4배
두꺼우면 ERA가 능력치를 반영한다.

다음에 할 것: 로테이션에 **관성**을 준다(직전 선발진을 우선하고 컨디션이
크게 나쁠 때만 교체). 그리고 1군 SP가 왜 9~12명까지 쌓이는지도 봐야 한다 —
콜다운이 `rated()` 낮은 순으로 내리는데 RP가 대체로 약해서 SP만 남는 것으로
보인다(부류는 보지만 SP/RP는 안 본다).

⚠ **성격 계수는 이게 해결된 뒤에 판단한다.** 지금 값(선발 합산 −0.24)으로는
근거가 안 된다.

### OVR–ERA 상관은 표본 60이라 단일 실행으로 못 쓴다

성격 계수를 판단하려면 이 지표가 먼저 깨끗해야 하는데, 실행마다
**−0.13 ~ −0.64**로 흔들린다. `abilitySpreadProbe`가 `ip >= 40`으로 거르니
사실상 선발만 남아 표본이 60명이고, 몇 명이 지표를 통째로 흔든다.

두 가지는 확인됐다:

- **능력치 평준화는 아니다.** OVR 상위25% vs 하위25% 차가 두 시즌 모두
  17~19점으로 유지된다 — 능력치가 성적을 만들 조건은 갖춰져 있다
- **프로브가 현재 OVR로 재고 있었다.** 시즌 중 성장한 신인이 "높은 OVR인데
  성적이 나쁜" 표본이 된다. 시즌 시작 OVR로 바꾸니 둘째 시즌 ERA 격차가
  0.02 → 0.51 → 1.79로 살아났다

⚠ **성격 계수 판단은 이 지표 위에서 해야 하는데 지금 신뢰도로는 못 한다.**
표본을 늘리려면 **여러 시즌을 합산**한다. 불펜을 포함하는 건 안 된다 —
마무리(고OVR·저ERA)가 섞여 상관을 인위적으로 강화한다.

### 병역 — 정원 제어가 두 경로로 갈려 있었다

선발이 주인공(W52, `advanceWeek`)과 NPC(오프시즌, `stores/game.ts`)로 나뉘는데,
**주인공 경로만 `maxTotal: 10`이 박혀 있었다**(규칙 파일 값은 13). 그걸 잡는
검사가 `test:military`에 있었지만 `game.ts`만 스캔해서 못 봤다 —
**검사가 있어도 보는 파일이 하나면 다른 경로는 그대로 샌다.**

별개 추첨이라 둘 다 뽑히면 정원 + 1이 되는 누수도 있었다(상무는
`career_status: "military"`라 로스터 캡이 안 걸린다). 상세는
[military.md §9~10](design/military.md).

## 알아두면 좋은 것

### 작업 습관

- **하네스를 먼저 돌려라.** 5-2에서 refs를 교체하자마자 INV3이 위반 990건으로
  "옛 팀 ID를 하드코딩한 스크립트"를 즉시 잡았다. 큰 변경 전후로 돌릴 것.
  단 **하네스는 slot.db와 Rust만 돈다** — `advanceWeek`(TS)를 안 거치므로
  거기 없는 것(관계도 등)의 불변식을 하네스에 넣으면 공허하게 통과한다.
- **svelte-check 숫자는 main과 대조해서 읽어라.** 기존 결함이 여러 개라 절대값은
  의미가 없다. `git stash -u` → 측정 → `stash pop` → 재측정으로 증감만 본다.
- **팀 목록·대회 카탈로그를 손으로 박지 말 것.** 정본은
  `resource/data/seeds/onepitch/*.csv|toml`이다.
  시드를 고쳤으면 `python scripts/build_refs_from_seeds.py`로 재생성한다.
  **규칙 TOML을 고치면 master.db용 JSON도 이 스크립트가 다시 만든다** —
  안 돌리면 Rust가 옛 규칙으로 돈다(6B에서 두 번 겪었다).
- **slot.db 스키마 변경은 `MIGRATIONS`로.** `CREATE TABLE IF NOT EXISTS`만으로는
  기존 슬롯에 반영되지 않는다(그 결함이 B3였다). 현재 `SCHEMA_VERSION = 4`.

### 테스트는 실데이터를 읽어라 (이번에 세 번 물렸다)

합성 데이터로 짠 테스트는 **통과하면서 결함을 통과시킨다.** Phase 6.5에서 세 번 겪었다:

1. **ID 충돌** — 합성 팀명(`TEAM_UNIV_T00`~`T49`)으로는 우연히 안 겹쳐 통과했다.
   `refs.json` 실제 팀 목록으로 바꾸니 32건이 잡혔다
2. **연봉 0 검사** — 테스트 헬퍼가 인라인 규칙(`with_contract: false`)을 써서
   **연봉이 0인 걸 검사**하고 있었다
3. **출신 분포 역전** — 유닛테스트는 다 통과했다. 실제 300명 규모로 돌려
   분포를 찍어봐야 대졸 57% / 고졸 28%(KBO는 반대)가 드러났다

→ Rust 테스트는 `generation_rules.json`·`refs.json`을 `std::fs`로 직접 읽는다.
→ **분포는 실제 규모로 돌려 숫자를 찍는다. 예측하지 않는다** —
  6B에서 "감독 생존 45~55%"라고 예측했다가 실측 13%로 틀렸다(_ledger P6-6).

### 이 코드베이스의 함정

- **어휘 드리프트가 이 코드베이스의 1번 버그 유형이다.** 지금까지 여섯 나왔고
  전부 "저장하는 쪽과 읽는 쪽의 이름이 다른데 타입이 안 잡아준" 경우다:
  1. 감독 능력치 3중 이름 드리프트 → 매치 엔진에 **하나도 전달되지 않았다** (P6-2)
  2. `TeamHistory` v1 필드 → 팀 상세가 빈 값, 새 게임 팀 선택이 **렌더 크래시** (P6-10)
  3. 코치 `specialty` 영문 4종 vs 데이터 한국어 6종 → 비교가 3곳 전부 false라
     **투수코치 능력치가 훈련 효율에 반영되지 않았다** (6C-5)
  4. `TEAM_SPORTS_UNIT` v1 팀 ID → 입대자가 **존재하지 않는 팀**으로 갔다 (R-5)
  5. `draftSystem`의 팀 ID 8개 → 매년 지명자 80명이 **유령 팀 소속**이 됐고,
     같은 유령 ID를 쓰던 신인 계약 배수는 전 구단이 1.0으로 떨어졌다 (7-1 D-1)
  6. 로스터 상한이 규칙 파일·Rust·TS 세 곳에 **각각 다른 값**으로 (7-1 D-3a)
  7. `militaryRank`를 TS 타입에만 넣고 Rust 구조체에 안 넣어서, NPC가 Rust를
     통과할 때마다 계급이 **조용히 사라졌다**. `syncNpcs`가 INSERT OR REPLACE라
     다음 저장에 DB 값까지 지워진다 (7-1 스모크에서 발견)
  → **Rust가 안 쓰는 필드라도 `NpcSaveState`에 있어야 한다.** 없으면 왕복에서
     버려진다. `npm run test:draft`의 "Rust 왕복 보존"이 이 부류를 지킨다.
  → 새 필드를 붙일 때 **저장·읽기·타입 세 곳의 이름이 같은지** 의심하고,
     가능하면 비교를 한 함수로 모아 테스트로 대조를 묶어라.
  → **표를 두 번째로 적고 있다면 이미 드리프트다.** 정본을 정하고 나머지는 지운다.
- **`cargo build`만으로는 `.node`가 안 바뀐다.** napi가 바인딩을 다시 만들어야
  하므로 `npm run build:native`를 돌려야 한다. 안 그러면 고친 Rust가 그대로인
  것처럼 보여 "고쳐도 안 된다"고 오진하게 된다 (7-1 D-3a에서 겪었다).
- **Rust 규칙 구조체는 snake_case, TS와 주고받는 것은 camelCase.** TOML에서 오는
  규칙에 `rename_all = "camelCase"`를 걸면 `missing field`로 죽는다.
- **결정적 난수는 대상마다 스트림을 분리한다.** 한 스트림으로 순차 생성하면
  앞쪽 개수가 바뀔 때 뒤가 전부 흔들려 디버깅이 불가능하다(P6-4).
- **정수 반올림이 기하 감쇠를 멈춘다.** 5 × 0.9 = 4.5 → 다시 5. 6C에서 20년 전
  헤어진 관계가 영원히 남는 걸로 나타났다. 수렴이 필요하면 1씩 미는 보정을 둘 것.
- **CRLF 파일이 섞여 있다.** Python 문자열 치환으로 여러 줄을 매칭할 때 실패한다.
  `i18n/index.ts`는 한글을 `\uXXXX` 이스케이프로 저장한다 — 스타일을 맞출 것.
- **ID 하드코딩은 반드시 드리프트한다.** `TEAM_SPORTS_UNIT`이 세 곳에 박혀
  있었고 Phase 5가 refs를 갈아엎자 **존재하지 않는 팀**이 됐다 — 새 게임 필터도,
  런타임 입대 처리도 그 ID를 썼다. ID는 `utils/ids.ts`에만 둔다(CLAUDE.md 규칙).
- **스태프와 선수는 이동 규칙이 다르다.** 감독의 `KBL → 고교`는 정상이고(직장),
  선수의 `대학 → 대학`은 불가다(학적). 한 표로 묶으면 어느 한쪽이 망가진다(P6-9).
- **상태 변경 지점이 여러 곳이면 훅 대신 정합 검사를 써라.** 주인공 teamId를
  바꾸는 곳이 5곳이라 6C는 훅을 안 박고 매주 "관계의 lastTeam이 지금 팀과 다른가"를
  본다. 어느 경로로 바뀌든 스스로 복구된다 — B1이 훅 누락으로 생긴 버그였다.
