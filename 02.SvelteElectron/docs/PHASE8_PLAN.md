## 0. 한 줄

**현재 성능은 측정된 적이 없다.** 그러니 최적화가 아니라 **계측**부터다.

BACKLOG §2가 정한 순서를 그대로 따른다:

```
1) 성능 목표 수치 합의   ← 이게 먼저다. 추측으로 최적화하지 않는다
2) 프로파일 → 진범 특정
3) 그것만 수정
```

이 프로젝트는 예측이 두 번 크게 틀렸다 — "감독 생존 45~55%"가 실측 13%였고,
Phase 7-5에서는 DESIGN이 적어둔 "스태프 15종 중 2종"이 실제로는 1종이었다.
**성능에서 같은 실수를 하지 않는다.**

### 1-3. 이미 보이는 구조적 후보 — **그러나 아직 진범이 아니다**

읽어서 눈에 띈 것이지 **측정한 것이 아니다.** 프로파일 전에는 손대지 않는다.

| # | 자리 | 왜 후보인가 |
|---|---|---|
| C1 | `backgroundLeague.runSimBatch` | 경기 **한 건마다 IPC 왕복**이다. 주 56경기 × 52주 ≈ 2,900회/시즌. 게다가 `entities` 배열을 매 호출 직렬화한다 |
| C2 | `getManagerRotationSense` | 경기마다 `entities.find()` 선형 탐색 ×2. 엔티티 6,800개 × 2 × 56경기 |
| C3 | `slotRepo.getAllNpcs` | `SELECT * FROM npc` 전량. 20시즌 누적 약 25,000행. **파일 크기가 아니라 매번 전 행을 파싱하는 게 부담**이다 |
| C4 | `advanceWeek`의 순차 IPC | 4개는 `Promise.all`로 묶여 있지만 나머지는 순차다 |
| C5 | SQLite 인덱스 | OnePitch가 같은 규모에서 **73초 → 24.75초**를 얻은 최대 요인이 인덱스 부재 해소였다 |

> C5가 가장 유력하지만 **그것도 추측이다.** OnePitch는 Rust 단독이었고 현행은
> 주간 처리 상당부분이 TS다 — 병목이 같은 자리에 있으리라는 보장이 없다.

## 2. 단계 분해

### P8-0. 계측 하네스 (선결 — 여기부터)

**아무것도 고치기 전에 숫자를 만든다.**

- [ ] `npm run measure:perf` 신설 — 1시즌·5시즌 벽시계 시간을 낸다
- [ ] **단계별 분해**가 핵심이다. 총 시간만 재면 어디를 고칠지 모른다:
      `주간 경기 시뮬 / NPC 성장 / 승강 / 시즌 종료(오프시즌) / DB 쓰기 / 그 외`
- [ ] IPC 호출 **횟수**와 **누적 페이로드 바이트**를 같이 센다 —
      C1이 진범이면 시간이 아니라 이 숫자로 먼저 드러난다
- [ ] slot.db 파일 크기·행 수를 시즌마다 기록

⚠ **하네스는 `advanceWeek`(TS)를 안 거친다** — slot.db와 Rust만 돈다.
그래서 기존 `npm run harness`로는 주간 처리 성능을 못 잰다.
`measure:perf`는 **실제 주간 경로를 타야** 의미가 있다.

### P8-1. 목표 수치 합의 (사용자 확정 필요)

계측 결과를 놓고 **무엇을 목표로 삼을지** 정한다. 후보 축:

- 1시즌 자동진행 벽시계 (예: "30초 이내")
- 1주 진행 체감 (예: "버튼 누르고 1초 이내")
- 20시즌 커리어 완주 시간
- slot.db 크기 상한

> **이건 내가 정할 수 없다.** "충분히 빠르다"의 기준이 게임 경험에 달려 있다.
> 계측 숫자를 먼저 보여드리고 거기서 정한다.

### P8-2. 진범 특정 → 그것만 수정

목표에 미달하는 항목만 손댄다. 미리 정해두지 않는다.

다만 **손대게 되면 이 순서**가 위험 대비 효과가 낫다:

1. **인덱스·쿼리** — 코드 변경이 없어 회귀 위험이 가장 낮다
2. **배치화(C1)** — `simGameBatchNative` 하나로 주간 경기를 한 번에 넘긴다.
   경기 결과가 바뀌면 안 되므로 **같은 시드로 결과 동일**을 회귀로 고정한다
3. **조회 캐싱(C2)** — `entities`를 Map으로 한 번만 인덱싱
4. **은퇴자 분리(C3)** — 파급이 크다. 아래 별항

### P8-3. 은퇴자를 `getAllNpcs`에서 빼기 (7-1 D-4b 이월)

- 근거 실측: `npm run measure:slotsize` (npc 행 781 B · 20시즌 약 25,000행 ≈ 25 MB)
- **파일 크기는 문제가 아니다.** 매번 전 행을 메모리로 올려 파싱하는 것이 부담
- ⚠ **게임 로직 여러 곳이 은퇴자를 참조한다** — 경력 이력·리그 기록·관계도.
  단순히 `WHERE career_status != 'retired'`로 자르면 그것들이 조용히 빈다
- 그래서 **P8-2에서 실제로 병목으로 확인된 뒤에** 손댄다

### P8-4. 회귀 · 문서

- [ ] `measure:perf` 결과를 문서에 남긴다 (숫자는 복제하지 말고 **재현 명령**을 적는다)
- [ ] 최적화가 **결과를 안 바꿨는지** 회귀로 고정 —
      같은 `worldSeed`에서 시즌 결과가 동일해야 한다
- [ ] `docs/design/performance.md` 신설

## 3. Phase 8에서 조심할 것

### 3-1. 결정성을 깨뜨리기 쉽다

병렬화·배치화가 **난수 소비 순서**를 바꾸면 같은 시드에서 다른 세계가 나온다.
Phase 7-7에서 이미 겪었다 — 로스터 캡의 `HashMap` 순회 순서가 결과를 바꿨다.

→ **최적화 전에 "같은 시드 → 같은 결과" 회귀를 먼저 만든다.**
   그게 없으면 최적화가 옳은지 알 수 없다.

### 3-2. "느려 보이는 곳"과 "느린 곳"은 다르다

`advanceWeek.ts`가 2,170줄이라고 거기가 병목인 건 아니다. 줄 수는 복잡도지
시간이 아니다.

### 3-3. 분해 리팩터링과 성능 작업을 섞지 않는다

`game.ts` 2,906줄 · `advanceWeek.ts` 2,170줄은 **상시 부채**(BACKLOG §5)지
Phase 8의 목표가 아니다. 성능 때문에 쪼개야 한다면 그건 측정이 말해준 뒤다.

## 5. Phase 7이 남긴 교훈 (Phase 8에도 적용된다)

Phase 7에서 **같은 형태의 결함이 16건** 나왔다. 전부 "정본이 둘 이상"이거나
"타입이 안 잡아주는 경계"였다. 전량 목록은 `docs/RESUME.md`에 있고, 규칙만 옮기면:

| | 규칙 |
|---|---|
| 1 | **표를 두 번째로 적고 있다면 이미 드리프트다.** 정본을 정하고 나머지를 지운다 |
| 2 | 폴백을 남길 거면 **대조 테스트를 같이 둔다** |
| 3 | Rust가 안 쓰는 필드라도 `NpcSaveState`에 있어야 한다 |
| 4 | **엔진을 만들었으면 호출부까지 확인한다** — 유닛테스트는 통과하는데 게임엔 없는 상태가 두 번 나왔다 |
| 5 | **`HashMap` 순회에 기대지 마라** — 순서가 결과를 바꾸는 자리가 실제로 있었다 |
| 6 | **회귀에 파일 목록을 하드코딩하지 마라** — 목록에 없는 파일이 옛 키를 계속 읽었다 |

6번은 Phase 8 직전에 배웠다. `test:staff`가 8개 파일만 훑고 있어서
`stores/backgroundLeague.ts`가 죽은 `manager.stats.handlePersonnel`을 읽는 걸
놓쳤고, **배경 리그 전 경기가 감독 능력치 50 고정으로 돌고 있었다.**
지금은 소스 136개를 전부 훑고, "`staffEffects`를 안 거치고 직접 읽는 곳"도 같이 센다.

→ Phase 8의 회귀도 같은 원칙으로 짠다. **목록이 아니라 조건으로 검사한다.**
