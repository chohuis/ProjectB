## 0. 한 줄

**현재 성능은 측정된 적이 없다.** 그러니 최적화가 아니라 **계측**부터다.

BACKLOG §2가 정한 순서를 그대로 따른다:

```
1) 성능 목표 수치 합의   ← 이게 먼저다. 추측으로 최적화하지 않는다
2) 프로파일 → 진범 특정
3) 그것만 수정
```

이 프로젝트는 예측이 두 번 크게 틀렸다 — "감독 생존 45~55%"가 실측 13%였고,
Phase 7-5에서는 DESIGN이 적어둔 "스태프 15종 중 2종"이 실제로는 1종이었다.
**성능에서 같은 실수를 하지 않는다.**

### P8-1. 목표 수치 합의 (사용자 확정 필요)

### P8-2. 진범 특정 → 그것만 수정

**P8-0이 진범을 특정했다** — `gameStore.save()`의 전량 재저장 (§6-3).
원안의 C1~C5 순서는 폐기한다. 그 다섯은 진범이 아니었다.

착수는 **P8-1 목표 합의 뒤에** 한다. 후보와 순서는 §6-4:

1. **저장 빈도** — 주당 3회가 왜 3회인지부터 확인 (코드 변경이 가장 작다)
2. **더티 셋** — `syncNpcs`가 바뀐 NPC만 넘기게
3. **시즌 블롭 분리** — `setSeason`에서 불변부 떼어내기

셋 다 **"저장이 누락되면 조용히 유실"** 계열이라, v1의 미저장 종료 유실 결함을
다시 부를 수 있다. 회귀(§P8-4) 없이 손대지 않는다.

### P8-3. 은퇴자를 `getAllNpcs`에서 빼기 (7-1 D-4b 이월) — **보류**

P8-0 판정: `getAllNpcs`는 **부팅 때 1회 50ms**고 주간 경로엔 없다. 병목이 아니다.

다만 은퇴자가 `gameStore.npcs`에 남아 **`syncNpcs`가 매번 같이 쓰는** 건 맞다 —
그건 P8-2의 더티 셋으로 자연히 빠진다. 별도 작업으로 올리지 않는다.

- 근거 실측: `npm run measure:slotsize` (npc 행 781 B · 20시즌 약 25,000행 ≈ 25 MB)
- ⚠ **게임 로직 여러 곳이 은퇴자를 참조한다** — 경력 이력·리그 기록·관계도.
  단순히 `WHERE career_status != 'retired'`로 자르면 그것들이 조용히 빈다

### P8-4. 회귀 · 문서 — **전제가 틀렸다 (P8-0이 반증)**

원안: "같은 `worldSeed`에서 시즌 결과가 동일해야 한다"를 회귀로 고정.

**그럴 수 없다.** 같은 시드로 두 번 돌려 세계 지문이 달랐다
(`a67c2d2e` vs `985ce7a4`, 같은 5,835개 항목). 원인은 버그가 아니라 설계다:

| | |
|---|---|
| **생성**은 결정적 | `generateLeagueRosterNative(seed=7)` 두 번 → 바이트 동일. worldSeed가 사람을 정한다 |
| **주간 시뮬은 비결정적** | `rand::thread_rng()`가 10개 모듈 **30곳**에 있다. `sim_game`도 그중 하나(`npc_sim.rs:292`)다 — 시드 입력 자체가 없다 |

CLAUDE.md의 Rust 패턴이 `thread_rng()`를 쓰라고 명시하고 있으니 **의도된 것**이다.
"같은 시드 → 같은 세계"는 생성에만 해당한다.

→ 그래서 최적화 안전망을 **통계·구조**로 바꾼다:

- [ ] **IPC 호출 횟수·페이로드 바이트**를 고정한다 — 실행 간 편차가 0.5% 미만으로
      가장 안정적인 지표다 (벽시계는 같은 설정에서 1.84~3.81s로 2배 흔들렸다).
      최적화가 이 수를 **의도한 만큼만** 줄였는지가 판정 기준이다
- [ ] 세계 규모 불변식은 기존 `npm run harness`가 이미 본다 — 최적화 후 재실행
- [ ] `fingerprint()`는 남겨둔다. **동치 판정용이 아니라** 엔진을 시드화하기로
      결정했을 때 쓸 도구다 (지금은 매번 달라지는 게 정상)
- [ ] `docs/design/performance.md` 신설 — 숫자 말고 **재현 명령**을 적는다

## 3. Phase 8에서 조심할 것

### 3-1. 결정성을 깨뜨리기 쉽다 — **그런데 애초에 결정적이지 않다**

원래 걱정: 병렬화·배치화가 난수 소비 순서를 바꾸면 같은 시드에서 다른 세계가 나온다.

P8-0이 확인한 실제: **주간 시뮬은 처음부터 비결정적이다** (§P8-4). 그래서
"같은 시드 → 같은 결과"로는 최적화를 검증할 수 없다. 대신 **IPC 횟수·바이트**를
본다 — 실행 간 편차 0.5% 미만이라 벽시계보다 훨씬 예민한 지표다.

단, 7-7의 `HashMap` 순회 결함은 여전히 유효한 경고다. 순서가 **분포**를 바꾸는
자리(로스터 캡 같은 우선순위 결정)는 비결정성과 무관하게 틀릴 수 있다.

### 3-2. "느려 보이는 곳"과 "느린 곳"은 다르다

`advanceWeek.ts`가 2,170줄이라고 거기가 병목인 건 아니다. 줄 수는 복잡도지
시간이 아니다.

### 3-3. 분해 리팩터링과 성능 작업을 섞지 않는다

`game.ts` 2,906줄 · `advanceWeek.ts` 2,170줄은 **상시 부채**(BACKLOG §5)지
Phase 8의 목표가 아니다. 성능 때문에 쪼개야 한다면 그건 측정이 말해준 뒤다.

Phase 7에서 **같은 형태의 결함이 16건** 나왔다. 전부 "정본이 둘 이상"이거나
"타입이 안 잡아주는 경계"였다. 전량 목록은 `docs/RESUME.md`에 있고, 규칙만 옮기면:

| | 규칙 |
|---|---|

| 3 | Rust가 안 쓰는 필드라도 `NpcSaveState`에 있어야 한다 |
| 4 | **엔진을 만들었으면 호출부까지 확인한다** — 유닛테스트는 통과하는데 게임엔 없는 상태가 두 번 나왔다 |
| 5 | **`HashMap` 순회에 기대지 마라** — 순서가 결과를 바꾸는 자리가 실제로 있었다 |
| 6 | **회귀에 파일 목록을 하드코딩하지 마라** — 목록에 없는 파일이 옛 키를 계속 읽었다 |

`stores/backgroundLeague.ts`가 죽은 `manager.stats.handlePersonnel`을 읽는 걸
놓쳤고, **배경 리그 전 경기가 감독 능력치 50 고정으로 돌고 있었다.**
지금은 소스 136개를 전부 훑고, "`staffEffects`를 안 거치고 직접 읽는 곳"도 같이 센다.

→ Phase 8의 회귀도 같은 원칙으로 짠다. **목록이 아니라 조건으로 검사한다.**

## 6. P8-0 실측 결과 (2026-07-31)

재현: `npm run measure:perf` (기본 W51 목표, 실제로는 W47 `draftObserve`에서 정지).
전체 리포트는 `docs/reports/perf_last.json`.

### 6-1. 한 줄

**주당 약 2~3초. 그 절반 이상이 "안 바뀐 것까지 통째로 다시 저장"하는 데 쓰인다.**

### 6-2. 주간 (고교 1학년, W0 → W47, 47주)

| | 값 |
|---|---|
| 주당 벽시계 | 평균 2.8s · p50 2.6s · p95 4.7s · 최대 6.3s |
| 분해 | IPC 76% · TS 24% |
| IPC | 주당 **107회 · 46 MB** |
| slot.db | 47주 후 **19 MB** (+ WAL 13 MB) |
| 부팅(새 게임) | 0.5s — NPC 5,596 · 스태프 포함 |

⚠ 벽시계는 같은 설정 5회 실행에서 **1.84 ~ 3.81s로 2배 흔들렸다.**
반면 IPC 횟수·바이트는 4,286~4,343회 / 1,844~1,877 MB로 **편차 0.5% 미만**이다.
→ **판정은 바이트로 한다. 벽시계는 자릿수만 본다.**

### 6-3. 진범 — 상위 3개가 71%

| 호출 | 47주 누적 횟수 | 시간 | 비중 | 페이로드 |
|---|---:|---:|---:|---:|
| `repo:syncNpcs` | 140 | 38.5s | **29%** | 888 MB |
| `repo:setSeason` | 140 | 34.3s | **26%** | 694 MB |
| `engine:simGameNative` | 2,647 | 19.7s | 15% | 203 MB |

앞의 둘은 **같은 원인**이다. `gameStore.save()`(`stores/game.ts:596`)가 한 번에

```
setProtagonist → setSeason → syncNpcs → setMeta
```

를 하고, 그게 **주당 3회** 불린다. `syncNpcs`는 매번 **NPC 5,596명 전원**을
`INSERT OR REPLACE`한다 — 실제로 그 주에 바뀐 건 수백 명이다.

호출당 비용 실측 (NPC 3,060명 · 2.73 MB 기준):

```
JSON.parse       6.5ms
SQL 쓰기        43.5ms   ← 70%
JSON.stringify  12.1ms
```

**SQL 쓰기가 지배적이고, 그 양은 "바뀐 수"가 아니라 "전체 수"에 비례한다.**

### 6-4. 그래서 손댈 곳 (P8-2 후보 — 아직 목표 합의 전)

| | 방향 | 예상 효과 |
|---|---|---|
| A | `syncNpcs`를 **더티 셋**만 쓰도록 — 변경된 NPC만 넘긴다 | 888 MB → 수십 MB |
| B | **주당 저장 3회 → 1회** — 왜 3번인지부터 확인해야 한다 | 상위 2개 모두 1/3 |
| C | 시즌 블롭(`setSeason`)에서 안 바뀌는 부분 분리 | 694 MB의 대부분 |

A와 B는 **독립**이라 곱해진다. 다만 셋 다 "저장 누락" 위험이 있는 변경이라
v1의 "미저장 종료 유실" 계열 결함을 다시 부를 수 있다 — 회귀 없이 손대지 않는다.

### 6-5. 남은 계측 공백

- 오프시즌: `SeasonEndModal.svelte` 안에 있어 못 잰다 (§P8-0)
- 프로 단계: 고교 1학년만 쟀다. 프로는 리그 수·로스터가 달라 재측정이 필요하다
- 20시즌 누적: `draftObserve` 정지 때문에 아직 한 시즌도 못 넘겼다

## 7. P8-2 결과 (2026-07-31)

### 7-1. P8-2a — 자동 진행 저장 주당 3회 → 1회

사용자 확정: **목표 주당 1초 · 손댈 범위는 저장 빈도만** (더티 셋·블롭 분리는 보류).

호출부 64곳을 뒤지지 않고 `gameStore`에 **배치 모드**를 넣었다.

| | |
|---|---|
| `save()` | 배치 **밖**이면 지금까지와 똑같이 즉시 쓴다 — 모달·페이지 55곳은 의미 변화 0 |
| `beginSaveBatch` / `endSaveBatch` | 여는 곳은 **`runAutoAdvance` 하나뿐**. `try/finally`라 중간 `return`·예외·정지 어디로 빠져도 밀린 저장이 확정된다 |
| `flushSave` | **주가 실제로 넘어갔을 때만** 부른다. `advanceWeek`은 pending을 밀어넣고 주를 안 넘긴 채 돌아오는 경우가 있어, 무조건 부르면 주당 2.15회가 된다 |

**위험 범위를 자동 진행 안으로 가둔 게 핵심이다.** 배치를 넓게 열수록 크래시 때
잃는 진행이 길어지므로, 최대 손실은 "그 주에 처리한 pending"이지 여러 주가 아니다.

**실측** (W0→W47, 반복 4회):

| | 전 | 후 |
|---|---:|---:|
| 주당 벽시계 | 2.79s | **1.24 ~ 1.48s** |
| IPC 주당 바이트 | 46.2 MB | **24.5 MB** |
| 저장 횟수 | 140회 / 47주 | **48회 / 47주 (1.02회/주)** |
| 1위 IPC | `syncNpcs` 29% | `simGameNative` 27% |

목표 1초에는 **못 닿았다** (1.24~1.48s). 남은 1위는 `simGameNative`
— 배경 경기 한 건마다 IPC 왕복이다 (원래 C1). 더 가려면 그걸 배치화하거나
`syncNpcs` 더티 셋을 해야 한다. **사용자 확정 없이 진행하지 않는다.**

### 7-2. 유실 회귀 — 이 변경의 안전망

저장을 미루면 "메모리엔 있는데 디스크엔 없다"가 **조용히** 생긴다. v1의
미저장 종료 유실이 그 계열이었다. 그래서 `measure:perf`가 끝날 때
**메모리 지문과 slot.db 지문을 비교**하고, 다르면 성능 수치와 무관하게 `exit 1`이다.

처음엔 이 검사가 오탐을 냈는데 **검사 쪽이 틀렸다** — 저장 경로는
`dehydrateToRepo`로 라이브 스탯을 병합해 쓰는데, 메모리 쪽 `npc.pitching.ovr`
(시즌 시작값)을 그대로 읽고 있었다. 같은 변환을 태워야 "쓰였어야 할 것 vs
쓰인 것"의 비교가 된다.

### 7-3. P8-2b — 시즌 롤오버 추출

`SeasonEndModal.svelte`의 세계 처리 ~200줄을 `usecases/seasonRollover.ts`로 옮겼다.
모달에는 표시와 사용자 선택만 남는다.

⚠ 옮기면서 **한 곳이 조용히 깨질 뻔했다.** 컴포넌트에서 `p`는
`$: p = $gameStore.protagonist`라 **반응형**이었다 — `processSeasonEnd`가
학년·계약을 바꾼 뒤의 값을 본다. 스냅샷으로 옮겼으면 졸업 후에도 옛
`careerStage`로 분기했을 것이다. `P()` getter로 바꿔 유지했다.
