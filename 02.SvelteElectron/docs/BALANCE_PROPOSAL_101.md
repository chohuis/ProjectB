## ① 고졸 직행 지명 8.3% → 목표 30~40%

**지금 코드.** `packages/engine-native/src/npc_sim.rs:3822`
```rust
const UNDRAFTED_SCORE: f64 = 78.0;
```
`determine_protagonist_draft`(같은 파일 `:3824~`)가 계산하는 `draft_score`가
이 문턱 아래면 고졸 미지명(대학/독립행)이다. 라운드는
`round = (11.0 - (draft_score - 78.0) * 0.40)`(같은 파일 `:3942`)로 78점에서
11라운드(끝)에 닿게 앵커돼 있다.

**왜 8.3%인가.** ⑭(시작 능력치 프리셋 전 스탯 일괄 −9, 2026-09-09)가 고졸
직행 지명을 "거의 보장"에서 "거의 반대편"으로 넘겼다(`BALANCE_BACKLOG.md`
결정⑭ 절). 원인은 `draft_score`의 두 축(리그 백분위 `pct` · 절대 재능
`ovr_norm`)이 전부 hero 고유 축인데, ⑭가 hero의 시작 OVR만 내리고 NPC 또래
분포는 그대로 둬서 hero의 상대적 위치(백분위·ovr_norm)가 체계적으로
낮아졌기 때문이다.

**단서 — 빠른 단일 프로브 (`probe-paths.cjs --path draft`, 씨앗 20260802,
4시즌, 12분27초).** 실제 `[진로산식]` 로그 두 건:

```
2028 highschool drafted=false  total=62.93  (pct=60.7 · ovrNorm=66.7 · ovr=70)
2029 independent drafted=false total=76.71  (pct=78.5 · ovrNorm=68.9 · ovr=71)
```

두 값 다 78 문턱을 밑돈다 — 특히 두 번째(76.71)는 겨우 1.3점 차로 떨어졌다.
이 정도 근접 미스가 흔하다면 문턱을 10점 낮추는 것만으로 상당수가 문턱을
넘을 것으로 추정된다. ⚠ **표본이 2건뿐이고 정책이 `draft:true`(독립을
적극적으로 노리는 자동 정책)라 실제 페르소나 플레이와 다를 수 있다** —
그래서 문턱 최종값은 진짜 12칸 측정으로 확정한다.

**후보값.** `UNDRAFTED_SCORE 78.0 → 68.0`. 라운드 직선의 앵커(78.0, 위 공식)는
**그대로 둔다** — 그러면 68~78점 구간은 `round`가 11 위로 계산돼 그대로
클램프되어 "11라운드 턱걸이"로 뽑힌다. 이것은 사용자가 정한 세 갈래
(상위픽/중간/미지명)에 "간신히 턱걸이"가 자연스럽게 얹히는 부작용이며,
라운드 분포 자체(1~11R 곡선)는 안 건드린다 — **한 번에 한 변수** 원칙을
지킨다.

**측정 완료 — 전후 12칸 (2026-09-10, `PB_SEEDS=20260802,777,31337
PB_ONLY=1-12 PB_SEASONS=12 npm run probe:a:simrun`, 성장 페르소나 ×

## ② 제구형(control)이 안 오른다 — ①과 같은 자리

**증상.** 짝 구성 12판(성향 셋 · 씨앗 하나)에서 4개 시작 프리셋 중
**control만** 최고 OVR이 80(30판 기준선) → 80(짝 12판)으로 **그대로**다.
나머지 셋은 전부 올랐다 — balanced 81→89 · power 81→87 · stamina
79→**88**(`docs/BALANCE_BACKLOG.md` "제구형만 안 올랐다" 절).

**이번 세션이 다른 표본(4프리셋×3씨앗·성장 하나)으로 다시 확인했다
(①의 before 배치).** 같은 그림이다 — control 최고OVR **79·80·77(중앙
79)**로 balanced(85)·power(85)·stamina(86)보다 뚜렷이 낮다. 표본이
달라졌는데도 재현된다는 점에서 "씨앗 하나의 우연"일 가능성은 낮아졌다.
control 프리셋의 진로도 3판 다 `pro_kbl`(군 미도달 2/3)이라 여전히 군을
잘 못 밟는 경향도 같이 보인다.

**①과 겹치는 흔적.** ①의 after(문턱 68.0) 결과에서 고졸 직행이
power 프리셋으로 쏠렸다(3/3) — control은 0/3 그대로였다. 두 안건이
가리키는 방향이 같다: **control 프리셋은 velocity 하위권 때문에
`calc_pitching_ovr`·드래프트 `ovr_norm` 양쪽에서 불리하다.**

**원인으로 짐작되는 자리.** 같은 문서 결정⑭ 절 §①: ⑭의 "전 스탯 일괄
−9"가 control 프리셋의 velocity를 유독 세게 깎았다(57→48 · 141km/h→131km/h
· **또래 백분위 1.8~2.4%, 하위 2%**). `calc_pitching_ovr`
(`growth_engine.rs:393`)에서 velocity 가중이 2.5로 가장 크므로, 하위권
velocity가 이후 훈련으로도 다른 스탯보다 회복하기 어렵고 ERA 산식에서도
velocity 비중이 커 실전 결과(승수·건강)까지 끌어내리는 것으로 보인다.

**되돌릴 값(이미 계산 확인됨 · 백로그에 명시).**
`velocity: 48 → 53 · command: 69 → 67`이면 `calc_pitching_ovr` 상 OVR 59가
그대로 유지된다(2.5×(+5) + 2.5×(-2) = +12.5-5=+7.5 → ÷12 ≈ +0.6, 반올림
전후로 59 유지). ⑭가 지킨 "성격 차를 정확히 보존한다"는 취지는
그대로다 — velocity 하위 2%라는 **파생 결과만** 완화한다.

**⚠ 반드시 같이 바꿔야 하는 두 자리.**
- `apps/ui/src/pages/new-game/NewGamePage.svelte:227` — 실제 게임이 읽는 표.

## ④ 위기집중력(clutch) · 견제(holdRunners) — OVR에 거의 안 남는 스탯

**수치 확인.** `growth_engine.rs:393` `calc_pitching_ovr` 가중은 구속2.5·
커맨드2.5·제구2.0·무브먼트1.5·스태미나1.5·멘탈1.0·회복0.5·**위기집중력0.3·
견제0.2**(합 12, ÷12). 0~100 만점 스탯 하나가 줄 수 있는 최대 OVR 기여는
가중×100÷12다 — 위기집중력 **2.5점**, 견제 **1.67점**(구속 20.8점과 비교하면
1/8~1/12). `growth_engine.rs:939`의 33~35세 에이징 감퇴 항목에도 이 둘은
빠져 있다 — 값을 올려도 커리어 내내 안 깎이니 "쌓아 둘 이유"조차 약하다.

**콘텐츠 쪽은 이미 절반 움직였다.** 2026-09-07 이벤트 스탯 재배분에서
견제를 쓰던 이벤트 슬롯 1곳 → **0곳**으로, 위기집중력은 10곳 →
**7곳**으로 줄었다(`BALANCE_BACKLOG.md` §16-3). 다만 이 7곳은 "장면이 그
스탯을 실제로 말하는 자리"라 데이터를 더 옮기면 문안과 효과가
어긋난다(같은 문서 경고).

**두 경로 — 사용자가 고를 것.**
- **(A) 그대로 두고 명문화.** "위기집중력"을 기계적 승부처 계수가 아니라
  이미 배선된 슬럼프 저항(사기가 무너져도 늦게·덜 빠진다)의 **서사적
  표현**으로 문서에 못박는다. 값 변경 없음 — "위기에 강함" 특성이 이미
  같은 처지다(반쪽만 산 특성 · `BALANCE_BACKLOG.md` §등급4단계).
- **(B) OVR 가중을 올린다.** 예: 위기집중력 0.3→0.8, 견제 0.2→0.4(합
  +0.7). 상쇄로 멘탈 1.0→0.65, 회복 0.5→0.15(합 −0.7)를 낮춰 총합 12를
  유지한다. **파급 범위가 넓다** — `calc_pitching_ovr`는 보직 적합도
  계산과 무관하지만(그건 `generation_rules.json`의 별도 가중), 드래프트
  백분위(`ovr_norm`)·에이징 총량·스카우트 랭킹에 전부 물린 값이라
  단독으로 재기 어렵다.

**제안.** (A)를 1차로 권한다 — 값 변경이 없어 다른 안건과 부딪히지 않고,
"위기에 강함" 특성건과 판단을 통일할 수 있다. (B)를 원하면 별도 세션에서
단독으로 전후 12칸을 재야 한다(이번 세션엔 시간이 없었다).

**확신.** 하 — 두 경로 다 실측이 없다. (A)는 값이 안 바뀌므로 실측이
필요 없다는 뜻이기도 하다.

## ⑦ 대가(cost)·갈래(선택지) 피로 겹침 — 정적 감사로 완결

**방법.** `resource/data/master/events/{mandatory,conditional,random}/**`를
전부 읽어 `cost.fatigueDelta`가 있는 이벤트를 추리고, 그 이벤트의

합을 계산했다(스크립트는 검사용 1회성 · 파일 편집 없음).

|---|---|
| `cost.fatigueDelta` 보유 이벤트 | **60건**(cost=8: 21건 · cost=12: 39건) |
| 합계 > 20 | **16건**(옛 문서 "33건 중 15건"에서 콘텐츠 증가분 반영) |
| 최대 합계 | **27**(`EVT_HS_Y3_LAST_CAMP` — cost12 + 옵션15) |

줄지만 **0이 되지 않는다**(옵션 자체 피로가 14~15인 5건은 cost를 0으로
없애도 여전히 20을 넘는다). 최대 27→23.

**후보 (나) 초과 16건만 대가를 관계/사기로 교체** — 20 초과분만 `cost`를

**제안 — (나).** 손대는 범위가 16/60건으로 최소이고 완전히 해소된다.
(가)는 39건을 다 건드리고도 문제가 남는다.

**확신.** 상 — 정적 감사라 재현 가능하고 확률적 요소가 없다. 다만 이

확정된다 — 그건 이번 세션에서 안 쟀다.

## ⑧ 프로초반 유니크가 얇다
